# TASK-DESIGN-034：设计基础数据目录与模板能力闭环

## 1. 背景

PPTD 已具备设计令牌、设计方向、页面配方、模板分析、版式能力摘要、图表主题和视觉评审，但这些能力仍分散在不同模块中。尤其是模板版式的 `hasTitle`、`hasBody`、`hasImage`、`columns` 和 `free` 已随文档持久化，视觉评审提示词却只包含版式名称、网格、字号和墨色，模型无法判断一个版式是否真的能承载图片或双栏内容。

本任务把“设计基础数据”定义成可执行的数据链，而不是新增一套与现有实现平行的组件库。

## 2. 数据分层

| 层级           | 现有落点                                             | 本任务边界                                     |
| -------------- | ---------------------------------------------------- | ---------------------------------------------- |
| 设计令牌       | `src/core/design/design-tokens.ts`、主题预设         | 继续作为颜色、字体、字阶、间距和效果的唯一来源 |
| 语义组件       | 配方生成的标题、卡片、轨道、图表、图片和装饰元素     | 后续以能力元数据描述，不复制渲染实现           |
| 页面配方       | `src/core/layout/recipes/`                           | 注册表是“可以真实渲染”的事实来源               |
| 模板版式能力   | `PresentationDocument.layouts[].capabilities`        | 合并进供模型使用的模板目标                     |
| 内容语义       | `SlideContent`、`CompositionFacts`、`PageDesignPlan` | 只读消费，不允许设计流程改写已审核内容         |
| 品牌与媒体资产 | 主题、模板分析、图片资源                             | 沿用现有资产与授权边界                         |
| 约束与降级     | `supports`、编译冲突、导出报告                       | 不静默删减内容；不满足时返回冲突或警告         |
| 质量基线       | 模板适配检查、视觉评审、固定样张                     | 后续统一汇总为可追溯目录                       |

## 3. 实施阶段

### 阶段 A：模板能力进入提示词（本次实现）

1. 定义仅供提示词使用的模板目标类型；版式可附带 `SlideLayoutCapabilities`。
2. `templateTargetForPrompt` 按版式名称，把当前文档已持久化的能力摘要合并到相关版式。
3. 不修改 `TemplateReviewTarget` 的持久化模型，不提高 `schemaVersion`。
4. 没有能力摘要的旧文档保持原行为，不猜测、不补造能力。
5. 补单元测试，覆盖能力合并、相关版式裁剪和旧数据兼容。

### 阶段 B：配方与语义组件目录

1. 为每个已实现配方声明展示名、页面意图、需要的内容块、图片要求、推荐容量和产出的语义组件。
2. 注册表启动时校验目录与 `RecipeId` 一一对应；目录不得声明没有渲染器的配方。
3. 设计提示词、版式选择器和导出报告消费同一份目录。

进度（2026-10-26）：已完成 renderer-backed 配方目录、语义组件角色、图片前置条件、最小栏数与容量说明；图片配方判定已改为从目录派生，避免与注册表维护两份名单。目录已随逐页设计请求送入 Rust AI 端口，并写入提示词；后端设独立 40 KB 上限，模型只能从当前设计方向允许且渲染器已实现的目录项中选择。

### 阶段 C：模板版式选择闸门

1. 将页面需求归一为标题、正文、图片、栏数和自由构图需求。
2. 只在模板声明的兼容版式中选择；没有兼容项时返回稳定错误码和建议。
3. 设计 Agent 不得通过删正文、删图片需求或改变页序来满足版式。

进度（2026-10-26）：已增加确定性兼容闸门和稳定错误码。图片页必须落在有图片占位的版式，双栏页必须落在至少双栏的版式，普通内容页必须有标题和正文占位；没有兼容版式时返回 `undefined` 并记录页码、意图、错误码和可读原因，不再静默退回文本版式。设计构建上下文保留完整问题列表，供后续 UI 和导出报告接入；未上传模板时不产生模板冲突。

### 阶段 D：样张与质量目录

1. 每个配方至少提供浅色、深色和容量边界样张。
2. 记录主题版本、模板版式、配方、关键组件和降级项。
3. 把样张纳入视觉回归，导出仍以原生可编辑对象为优先。

进度（2026-10-26，第一片）：已建立全部已实现配方的四象限样张矩阵（浅色、深色、容量边界、模板兼容），每项都要求原生对象检查；AI 的概念、方向和逐页设计请求现在都显式携带模板版式能力摘要。导出报告新增统一设计审计，记录 Schema、配方目录/样张矩阵版本、主题/模板标识、组件计数、版式能力与使用数，以及动画、组合和通用导出警告等降级项。配方 ID 尚未持久化，审计明确报告覆盖率为 0，不根据几何猜测。

## 4. 本次验收

- 使用上传模板且文档保存了版式能力时，传给视觉评审/修复模型的相关版式包含能力摘要。
- 只发送当前文档引用的版式；没有引用时沿用最多 12 个版式的既有上限。
- 同名版式找不到能力时不生成虚假字段。
- 不改变内容 revision、设计 revision、撤销栈或持久化 Schema。
- `template-review-target` 相关单测、TypeScript 类型检查和 ESLint 通过。

## 5. 后续完成标准

完整闭环完成后，新增主题、模板或配方必须能回答：使用哪些令牌、承载哪些内容、生成哪些组件、依赖哪些版式能力、容量边界是什么、失败如何报告、由哪个固定样张验证。组件不能脱离配方单独承诺可用性，模板版式也不能只靠名称推断能力。
