# 0017 导出视觉回归比对

## 状态

已采纳（2026-10-23）。

## 背景

导出侧的检查一直停在结构层：`validatePresentationForExport` 看的是内容有没有审核、元素有没有出界、文字会不会溢出，`validatePptxPackage` 看的是包结构对不对。两者都无法回答一个最朴素的问题：**导出的文件看起来还和以前一样吗？**

结构检查看不见的问题很多：颜色被写成主题色而不是直接值、文本框的内边距让文字挪了位置、图片的裁剪框算错了一个百分点、母版的背景没有被真正继承。改一行导出代码就可能悄悄改变整份文件的观感，而现有的检查全部通过。

## 决策

1. **比对的是"渲染出来的文件"，不是"文件里的 XML"**。检查把导出的 PPTX 交给一个真正的演示文稿程序渲染成图片，再把图片和参考图逐像素比对。结构检查继续存在，两者互补。
2. **渲染器是一个可替换的外部程序**。首选 PowerPoint——文件就是给它用的，它渲染出来的才是用户会看到的；本机没有 PowerPoint 时退回 LibreOffice。每个渲染器有自己的一份参考图，因为 PowerPoint 画的图和 LibreOffice 画的图本来就不是同一张图。
3. **参考图绑定生成它的那台机器**。换一个 PowerPoint 版本、换一个渲染器或少装一个字体，画出来的图就不同。因此参考图按渲染器分目录存放，换机器需要重建，而不是让全局的检查一直红着。
4. **阈值要盖住渲染器自身的噪声**。抗锯齿和字距提示会让同一份文件两次渲染出几个百分点的差别，因此比较有两个参数：颜色通道的容差（默认 8/255）和允许变化的像素比例（默认 0.2%）。超过容忍度才算回归。
5. **尺寸不同一律算回归**。缩放是版式变化，不是渲染差异，按"全部不同"报告只会掩盖真正的原因。
6. **回归要能一眼看出改了什么**。检查会写出一张差异图：原图变成浅灰，变化的像素标成红色。
7. **PNG 自己解码**。PowerPoint 写的是调色板 PNG（`colorType=3` + `PLTE`），所以仓库里有一个不依赖任何图像库的 PNG 编解码器（`src/core/rendering/png.ts`，用 `fflate` 解压、CRC32 自己算）。隔行的图片明确拒绝，而不是读成一张错图。
8. **纯逻辑在核心层，工具在 `tools/`**。像素比较、PNG 编解码、回归判定都是纯函数，放在 `src/core/rendering/` 里，有单元测试；真正调用外部渲染器、读写文件的部分放在 `tools/visual-regression/`，因为 `src/` 里的代码不依赖 Node。

## 与需求基线的对应

需求基线 10.4 要求对固定测试文件"生成编辑画布截图 → 导出 PPTX → 转换为 PDF 或图片 → 对比关键对象位置、字体、换行和裁剪 → 将差异纳入回归测试"。本决定覆盖第 2、3、5 步，第 4 步由逐像素比对实现：位置、字体、换行、裁剪的任何变化都会改变像素。

第 1 步的参考来源不同：本实现以**一份被接受过的导出结果**作为参考，而不是每次现生成的画布截图。原因是画布截图与导出文件共享同一套假设——导出端和画布端同时错了同样的地方时，两边仍然一致，检查却看不出来；而参考图是一次人工确认过的正确结果，导出端一旦跑偏就会被抓住。代价是参考图与机器绑定，换渲染器或换机器要重建。

浏览器画布与 PowerPoint 的断行算法不同，两者逐像素比较会淹没在假阳性里，因此不作为参考。

## 影响与边界

- **参考图必须人工看一眼再提交**。第一次运行时检查会生成参考图并失败，提示先检查再提交；确认过之后重跑才是绿的。`PPTD_VISUAL_BASELINE=update` 可以重建参考图。
- **没有渲染器时检查会跳过，而不是失败**。CI 上没有 PowerPoint 就没有视觉回归结论，这一点必须如实说出来，不能假装检查过了。
- **参考图与机器绑定**。PowerPoint 升级、字体变化都会让基线失效，这时候需要重建。
- **只覆盖夹具里的两页**。夹具固定写死了文字、表格、图片和形状，覆盖导出最主要的几种对象，但不是整份产品的保证。
- LibreOffice 只能渲染第一页（`--convert-to png` 的限制），所以用 LibreOffice 时只有第一页参与比对。
- `tools/` 不在 `tsc -b` 的检查范围内：`src/` 保持不依赖 Node，工具里的 Node 调用因此不受类型检查，只受 ESLint 和运行时约束。
