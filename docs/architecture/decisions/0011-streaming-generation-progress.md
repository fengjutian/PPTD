# 0011 生成过程的流式进度

## 状态

已采纳（2026-10-22）。

## 背景

分批生成把等待时间压到了"单批耗时"量级，但用户仍然只能看到批次级的进度：知道在写第 2 批共 4 批，不知道正文写到第几页。等待二十页草稿时，"已写 11 页"比"第 2/4 批"更能让用户判断还要等多久、要不要取消。

厂商提供 OpenAI 风格的 SSE 流式响应，MiniMax 兼容这一协议。把响应改成流式接收，可以在生成过程中持续汇报进度。

风险有两个：厂商的流式协议细节无法在本地验证；协议不兼容时不能让生成失败。

## 决策

1. SSE 解析是纯函数。`SseParser` 吃网络分片、吐出正文增量，不碰 HTTP。协议细节只影响这一个文件，可以用固定样例直接测。
2. 解析器容忍脏数据：心跳行、结束标记、空内容、坏掉的 JSON 行都不能影响后续解析。
3. 流式失败一律带 `AI_STREAM_FAILED` 前缀，命令层见到这个前缀就退回一次性请求重新生成。流式只是进度反馈的增强，不该让生成失败。
4. 取消与超时的错误码不带这个前缀：取消立刻中止，超时直接报错，两者都不退回。
5. 已写页数靠数流式文本里 `"speakerNotes"` 出现次数估算——每个页面对象恰好有一个该字段。这是进度提示用的估算，不参与任何内容判定。
6. 正文分批并行，各批只知道自己写到第几页。进度事件带 `key` 区分请求，前端按 key 汇总：同一批次重复上报取最新值，各批页数相加就是整份草稿的进度。
7. 进度事件每累计 200 个字符发一次，避免每个增量都发事件。

## 影响

- 生成期间可以显示"已写 N 页"，进度粒度从批次级降到页级。
- 厂商流式协议若有差异，用户察觉不到：生成结果一致，只是进度退回批次级。
- 流式响应只用于生成阶段。视觉评审是多模态请求，不走这条路径。
- 页面进度是估算值：模型输出的 JSON 字段顺序若变化，估算会偏。它只影响进度显示，不影响生成结果。
