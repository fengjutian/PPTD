# 0004 内容哈希、内容引用与 revision 隔离

## 状态

已采纳（2026-10-21）。

## 背景

V0.1 的页面同时保存 `content` 和视觉元素。此前文本编辑直接修改元素，只有第一个文本元素会顺手写回标题；正文、结构化块和设计命令无法可靠区分内容变更与设计变更。自动保存、AI 设计和后续的冲突检测都需要一个稳定的内容标识。

## 决策

1. `SlideContent` 保存 `title`、`body`、可选的 `blocks`、`speakerNotes`、`status` 和 `contentHash`。
2. `contentHash` 使用同步的 FNV-1a 64 位哈希，输入为标题、正文、备注和结构化块；审核状态不参与哈希。哈希不是安全摘要，只用于变更检测和设计任务固定内容版本。
3. 文本元素通过 `contentRef` 声明语义角色：
   - `title`：编辑时写回 `content.title`。
   - `body`：编辑时写回 `content.body`，并把结构化块收敛为单个段落，避免块数据与正文不一致。
   - `decorative`：只属于设计层，不修改内容。
   - 未声明的旧元素沿用“第一个文本元素是标题”的兼容规则。
4. 命令的内容/设计领域由 `commandDomain(command, document)` 判断。新增装饰文本、图片、形状、变换、层级和锁定只递增设计 revision；标题/正文编辑及内容绑定的删除递增内容 revision。
5. AI 生成文档通过 `replaceDocument` 作为一次可撤销事务进入编辑历史，不再调用清空历史的 `loadDocument`。
6. 复制内容绑定文本时，副本标记为 `decorative`，避免两个视觉元素同时写同一个内容字段。

## 影响

- 设计命令不会静默改写已审核内容，内容 revision 和 `contentHash` 可以用于后续的审核失效与冲突提示。
- 结构化块目前由 AI 生成和保存；画布直接编辑正文会降级为段落块。块级可视化编辑是后续工作。
- `decorative` 文本暂不进入内容模型；需要参与审核的自由文本应先扩展内容块命令，而不是直接标记为标题/正文。
