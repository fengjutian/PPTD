# 0079 评审概念分与总分封顶

## 状态

已接受（2026-10-24）。

## 背景

视觉评审已有 `distinctivenessScore`，但它只问“有没有设计想法”，执行分仍然可以把一个概念空洞的页面推到 80 分以上。结果是一套“很精致但没有观点”的稿子拿到高分，修复循环继续打磨细节，而不是回到概念。

## 决策

### 1. 概念分是可选分数，不是新门

`VisualReview` 与逐页 `slideScores` 增加可选 `conceptScore`（0–100）：

- 整册：能否用一句话说出整册 idea；换掉客户名或标题后是否仍成立。
- 单页：能否用一句话说出这一页的 idea；换一个主题是否仍成立。

缺失时保持 `undefined`，旧评审、旧模型响应与旧测试桩不需要该字段。

### 2. 低概念分确定性地封顶

归一化完成后、返回评审前执行：

- 概念分 < 60 → 总分不超过 69；
- 逐页概念分 < 60 → 该页总分不超过 69；
- 记录 `conceptCapApplied: true`，报告显示“（总分已封顶）”。

封顶在 `normalizeVisualReview` 的 `applyConceptCap` 中完成，不在提示词里要求模型自行压分。模型可以给 95 的执行分，系统仍会把空概念压到 69。

### 3. 评审循环仍可继续

封顶会降低 `overallScore`，评审循环据此继续尝试修复。修复计划目前仍以版式/配方为主，不能“补一个概念”；如果多轮仍低，任务照常产出并报告低概念分，不阻断。

### 4. 报告与合并

- 批次合并保留最低概念分；整册总览的概念分优先。
- `mergeReviews`、`slideReviewFromBatch`、`batchReviewFromSlides` 都保留 `conceptScore` 与 `conceptCapApplied`。
- 设计质量报告显示整册与逐页概念分；封顶时注明原因。

### 5. 不持久化到评审历史

`ReviewTrace` 仍只存总分、问题数与逐页总分；概念分属于当次报告。若未来要在版本历史里回看概念分，需要扩展 Schema 并迁移，当前不做。

## 后果

正面：

- 概念空洞的执行型页面不能靠细节拿高分。
- 报告能明确指出“不是执行问题，而是没有 idea”。
- 封顶是确定性的，模型无法用措辞绕过。

代价与限制：

- 概念分仍是模型主观评分，需要真实样本校准；提示词只给出定义，没有人工标注基准。
- 封顶可能压低本来就朴素但合适的稿子；60/69 是经验阈值，可按真实评审调整。
- 修复循环目前无法真正“加概念”，低分可能触发无效轮次；任务仍会完成并报告。
- 历史版本不显示概念分。

## 验证

- `visual-alignment.test.ts`：概念 40 → 总分 69、逐页 69、`conceptCapApplied`；概念 80 → 总分保持 92。
- 全量测试、类型检查、ESLint、生产构建、`cargo fmt --check`、`cargo check` 通过。

## 备选方案

- **概念分低于阈值直接失败**：会把“朴素但合适”的稿子判死；封顶更可解释。
- **把概念分做成独立人工审核**：质量更高但成本大，当前先用模型分 + 确定性封顶。
- **加权平均**：执行分仍可淹没概念分，无法表达“概念是一票否决”。
- **让模型自己执行封顶**：不可靠，也无法测试；确定性逻辑必须在代码里。
