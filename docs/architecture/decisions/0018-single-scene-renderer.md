# 0018 缩略图与画布共用一份渲染

## 状态

已采纳（2026-10-22）。

## 背景

左侧缩略图原本自己复制了一份画布的渲染逻辑：元素用百分比定位，文字、图表、表格一律传一个写死的 `scale = 0.18`，形状的描边宽和圆角半径再乘 0.3，并且配了一套只属于缩略图的 CSS（`thumbnail-text`、`thumbnail-image`、`thumbnail-chart` 等）。

问题不在于"两处代码不一样"，而在于缩略图那条路径上的比例是**没有单位的**。`scale` 在画布上的含义是"每个 EMU 占多少像素"（约 7.9e-5），缩略图却传了 0.18，相差约 2000 倍；字号按 `pt × scale × 914400 / 72` 换算后变成几万像素，被 `overflow: hidden` 裁掉——于是**缩略图里所有文字都是空的**，只剩形状和图片；封面页那几行细横线就是被裁剩的巨型字形。此外还有三处独立的偏差：缩略图背景写死 `#FFFFFF`（画布用 `slide.background`）、表格内边距和边框写死像素（不随比例缩放）、描边与圆角把 pt 当 px 用（画布放大时也不跟着变）。

结果是：预览和画布必然对不上，而且画布每改一次样式，缩略图都要跟着改一次，改漏了不会有任何报错。

## 决策

1. **缩略图就是画布**。新增 `SlideScene` / `SlideElementFrame` / `SlideElementContent`，画布与缩略图渲染同一个页面时走同一份代码、同一套 CSS 类（`.slide-element` / `.shape-fill` / `.image-fill`），不再有 `thumbnail-*` 这一套平行样式。
2. **比例只有一个单位**：`sceneScale` 表示"每个 EMU 占多少像素"。画布的比例来自画布宽度，缩略图的比例由 `ResizeObserver` 量出自己盒子的宽度后除以页面宽度得到。字号、描边宽、圆角半径都用 `ptToPx` 按同一个比例换算，文字在两个视图里是同一个比例关系。
3. **表格的行高与边框用 `em`**。表格内边距和边框宽度跟随字号，缩略图里的表格才是画布里那张表的等比缩小，而不是一堆大边框的空格子。
4. **背景与宽高比来自文档**。缩略图用 `slide.background` 作背景，宽高比跟随页面比例（不再固定 16:9），因此非 16:9 的页面也不会被裁错。
5. **pt 一律换算成像素**。形状的描边宽与圆角半径不再把 pt 当 px 用（`13.33 in × 960 px` 的画布上 1 pt 恰为 1 px，改动前后视觉一致；换比例或换页面尺寸时才显出差别）。

## 影响与边界

- **缩略图里的文字断行位置未必与画布逐字相同**。字号按比例缩小后重新断行，这是浏览器断行算法的固有差异（同 `0016` 记录的换行差异），不是渲染路径分叉造成的。
- **图表仍是近似**。折线图的描边宽度用 `non-scaling-stroke`，不随页面比例缩放，缩略图里相对更粗；图表的分类文字比例正确。
- **缩略图第一次绘制需要一次测量**。`ResizeObserver` 回调在首次布局后触发；在没有 `ResizeObserver` 的环境（如服务端渲染的测试）里比例保持 0，静态标记不画元素，页面其余部分不受影响。
- **导出侧不受影响**。本决定只改画布与预览的绘制路径，导出仍按 `pt` 写入 PPTX。
