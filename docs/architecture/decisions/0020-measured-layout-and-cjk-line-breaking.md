# 0020：测量驱动的排版与中文断行纪律

## 状态

已接受（2026-10-22）。

## 背景

编辑式双栏页把内容区高度平均切成若干等份槽位，每一条要点在槽位里垂直居中。这个做法在所有要点长度相同时看不出问题，但实际正文长短不一：一条两行、一条一行的要点拿到同样的槽高，居中之后两行要点上下留白少、一行要点上下留白多，于是分栏线之间的距离虽然相同，文字块之间的真实空白却忽大忽小，整栏的节奏被打断。

右侧引文面板同样按固定比例切分：引号固定在顶部 0.02，引文固定在 0.36，两者之间是写死的空隙。引文短时空隙大得能塞进一行字，引文长时引文底部会撞上下方的横线和"关键摘录"标签。字号则按字符个数猜（超过 60 字用 16 号、超过 40 字用 18 号、否则 22 号），完全忽略了面板的实测宽度，同一套引文在宽窄不同的面板里会出现三档不同的大小。

此外，全仓库的文本换行由三套彼此独立的代码决定：核心层用整段宽度除以行宽估算行数，画布渲染器用贪心逐字换行，导出时由 PowerPoint 自行换行。三者对"这一行在哪里断开"的判断并不一致，导致质量门预测的行数和画布实际画出的行数可能不同——质量门说没有溢出，画布上却已经溢出了。

## 决策

### 测量驱动的流式布局

1. 新增 `src/core/rendering/flow.ts`。一栏要点的每一行按实测高度排布，不再平分槽位。
2. 同一栏的所有要点共用一个字号。字号从期望值向下搜索，直到内容加上最小间距能放进可用高度。某一条比其他的长，不允许它单独变成小字号。
3. 所有行之间的间距相同。剩余空间平均分配给这些间距，并受最大间距限制：内容很少的一栏不能被拉散成互不相干的若干条。
4. 剩余空间超过间距上限时，整栏在可用空间内居中，空白不会全部堆在最后一条下面。
5. 编号占位的高度是正文一行的高度，不是整行的高度。编号因此与每一条的首行齐平，编号列读起来是一条直线。

### 引文面板

6. 引号、引文、横线、"关键摘录"标签按实测高度排布。引号保持自身的大小，不再为了塞进面板被缩小成页面里最小的对象。
7. 引文字号从大到小搜索，取第一个能放进可用区域的字号。字号有上限：引文是展示对象，但比页面标题还大的引文会喧宾夺主。
8. 引文在引号与横线之间的区域里居中，横线与标签之间保持明确间距，线不再切进文字。

### 中文断行纪律

9. 新增 `src/core/rendering/cjk-linebreak.ts`，实现 PowerPoint 对中文文本同样遵守的三条规则：行首不出现收尾标点（标点悬挂到右边距），行尾不出现起首标点（标点与其配对字符一起下移），西文单词和数字不被拆到两行。
10. 核心层的 `estimateTextLines` 改用这个断行器。画布渲染器使用同一个断行器，于是质量门预测的行数、编辑器画出的行数、评审图片里的行数是同一个数。
11. 断行器是纯函数：它接收每个字符的宽度，不自己测量，因此核心层依然不依赖浏览器和桌面运行时。

## 结果

- 一栏要点的行距恒定，与各条文字的长短无关。
- 引文面板不再有写死的空洞，也不再出现横线压住标签的情况。
- 质量门与画布渲染器对同一段文字给出相同的行数。
- 排版规则集中在一个模块里，导出端要接入同一套断行时只需替换一个调用点。

## 未覆盖

导出时文本的换行仍由 PowerPoint 决定，不由本仓库决定。核心层与画布渲染器现在预测的行数与 PowerPoint 实际渲染的行数一致（本轮用真实渲染验证过），但断点的具体位置仍可能不同。彻底对齐需要导出端也使用同一套断行规则，属于导出保真的范畴，不在本次改动内。
