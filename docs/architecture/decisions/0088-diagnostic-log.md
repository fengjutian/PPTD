# 0088 失败诊断日志落盘

## 状态

已接受（2026-10-25）。

## 背景

生成、设计、导出或保存失败时，界面只在状态栏留一句话（例如“AI 设计生成失败：……”）。这句话在用户下一次操作时就被覆盖，应用退出后彻底消失。应用数据目录下只有 `pptd.sqlite3`、`recovery/`、`templates/` 和渲染缓存，没有任何运行日志；WebView 只写它自己的诊断文件。

结果是：故障只能靠用户复述，而用户通常只记得“报错了”。2026-10-25 的一次真实排查里，方向门从两个方向扩到四个之后用户报告“生成 PPT 报错”，`%APPDATA%`、`%LOCALAPPDATA%`、Windows 事件日志和测试记录都无法回答“是超时、限流、模型合同不符，还是预览渲染失败”。这次排查本身证明了缺口。

AGENTS.md 第 6 节要求长任务“必须支持取消、进度报告和可诊断错误”。进度已经有流式事件，错误目前只有 UI 文案。

## 决策

### 1. 一个只追加的 JSONL 文件

新增两个 Tauri command：

- `append_app_log(entry)`：追加一条记录；
- `app_log_location()`：返回日志文件绝对路径。

文件位于 Tauri 的 `app_log_dir`，Windows 上是 `%LOCALAPPDATA%\com.pptd.desktop\logs\app.log`。每行一条 JSON：

```json
{
  "at": "2026-10-25T14:00:00.000Z",
  "level": "error",
  "code": "AI_DESIGN_JSON_INVALID",
  "message": "AI 设计生成: slides.2.layout 不是已知版式",
  "context": { "slides": 6 }
}
```

### 2. 记录边界

只记录三类信息：

| 字段      | 内容                                                   |
| --------- | ------------------------------------------------------ |
| `code`    | 稳定错误码（`errorCodeOf` 从 `CODE: detail` 前缀提取） |
| `message` | 失败阶段 + 原始错误文本，用于人读                      |
| `context` | 计数与布尔量：页数、方向数、是否有模板、文档 revision  |

明确不记录：正文、演讲备注、表格/图表数据、图片数据、API Key、模型原始响应、文件内容。日志比项目文件更容易被随手转发，不能变成文稿的副本。

### 3. 上限与轮转

- 单条 `message` 2 000 字符、`code` 80 字符、`context` 4 000 字符；
- 超长 `context` 不截断内容，只写 `{ "truncated": true }`，避免“截断后的半段正文”反而泄漏；
- 单文件 2 MB，超出后重命名为 `app.log.1`，只保留一份历史。

### 4. 永不反向影响业务

- 前端 `recordAppLog` 是 fire-and-forget，吞掉所有异常；
- Rust 侧在 `spawn_blocking` 里写盘，用互斥锁串行化追加；
- 浏览器预览没有 IPC，直接跳过；
- 日志写入失败只产生一个错误码，调用方照常抛自己的业务错误。

### 5. 接入点

| 阶段        | 位置                         | 上下文                     |
| ----------- | ---------------------------- | -------------------------- |
| 导出 PPTX   | `handleExport` 的 catch      | 页数、是否有模板           |
| AI 内容生成 | 生成草稿的 catch             | 请求页数                   |
| AI 重新生成 | 重新生成的 catch             | —                          |
| AI 设计生成 | 设计阶段的 catch             | 页数、模式、是否有模板     |
| 方向提案    | `directionGate` 的提案 catch | 需要的方向数               |
| 方向预览    | 每个方向预览的 catch         | 该方向的 preset            |
| 方向数不足  | `candidates.length < 4`      | 收到数、渲染成功数（warn） |
| 自动保存    | 自动保存的失败回调           | 起始文档 revision          |
| 打开/保存   | 两个操作的 catch             | 页数                       |

### 6. 用户可见入口

设置 → 模型服务 → “诊断日志”，显示文件路径和“不含正文、备注或图片”的说明。浏览器预览显示“没有本地日志”。不再需要用户去猜目录。

## 后果

正面：

- 失败可以事后复查，错误码可以 grep，可以按阶段统计失败率；
- 排查“生成报错”时不再依赖用户复述；
- 方向门的静默回退（四个方向不足四个）从“不可见”变成一条 warn。

代价与限制：

- 多一个 IPC command 和每次失败一次磁盘写入；
- 只覆盖前端显式 `catch` 的路径；Rust 侧未捕获 panic 仍然只进 stderr；
- 没有自动上报，需要用户或开发者手动取文件；
- 日志不含正文，因此不能复现“模型对某段内容的具体反应”，只能定位阶段与错误码。

## 备选方案

- **`tauri-plugin-log`**：功能更完整（目标、轮转、格式），但要新增插件依赖和 capability，输出格式不可控；当前只需要一个可 grep 的 JSONL 文件，不采用。
- **写进 SQLite**：复用现有数据库，但诊断文件需要能单独取出并附在反馈里，数据库不适合；不采用。
- **只打 console**：开发模式可见，打包后不可见，等于没有；不采用。
- **记录完整错误对象/正文以便“更好复现”**：违反 AGENTS.md 第 6 节的日志脱敏要求；不采用。
