# 0010 持久化的可测边界与写入冲突处理

## 状态

已采纳（2026-10-22）。

## 背景

AGENTS.md 要求项目保存"采用临时文件、刷盘和安全替换；中断后必须保留上一个有效版本"，并要求持久化改动"必须覆盖保存中断、损坏输入和恢复场景"。

实际覆盖情况是：

- 恢复链路（`save_recovery` / `load_recovery` / `clear_recovery`）完全没有测试。命令依赖 `tauri::AppHandle` 取应用数据目录，单元测试无法构造。
- 保存中断没有测试，而且**真实存在一个缺陷**：Windows 上只要还有句柄指向目标文件，替换就会失败并返回 `FILE_REPLACE_FAILED: 拒绝访问`。自动保存与手动保存同时触发、或保存时另一个任务正在读文件，都会让用户的保存凭空失败。

## 决策

1. 恢复命令拆成薄命令层与可测的内部函数：`save_recovery_at` / `load_recovery_at` / `clear_recovery_at` 接受路径，命令层只负责解析应用数据目录。行为不变，只有可测性变了。
2. 同一进程内的写操作串行化。自动保存与手动保存可能撞在一起，把写操作排成队比让用户看到一次失败的保存更合理。
3. 替换目标文件失败时重试五次，间隔递增。Windows 上占用目标文件的句柄通常很短命，重试就能挤过去；跨进程或真正的权限问题仍会如实报错。
4. 恢复副本的损坏必须报错而不是返回半个文档：损坏的恢复文件返回 `RECOVERY_JSON_INVALID`，不存在的恢复文件返回空。
5. 保存中断的可观测后果只有一个——读者不能看到写了一半的文件。用并发读者测试守住这个不变量：反复替换大文件，同时另一个线程持续读取，读到的内容必须始终是完整的旧版本或完整的新版本。

## 影响

- 恢复链路现在有测试覆盖：往返、内嵌图片的落地与还原、损坏文件、无恢复文件、清除恢复文件与资源目录。
- Windows 上的并发保存不再偶发失败。跨进程的占用冲突仍然存在，靠重试窗口缓解，不做跨进程锁。
- 写操作串行化意味着一次写入期间其它写入等待；项目文件写入是毫秒级操作，影响可忽略。
- 测试没有模拟"进程被杀死"这种真正的中断。真正的不变量由"先写临时文件再原子替换"的结构保证，并由并发读者测试守住可观测部分。
