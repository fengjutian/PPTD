# 0022：视觉评审基于导出的真实 PPTX

## 状态

已接受（2026-10-22）。

## 背景

前三波把排版内核、AI 的设计话语权都改到位了，但评审环节一直没有闭环。

视觉评审模型看的是 `renderPresentationForVisualReview` 在浏览器画布上重绘出来的图片。那是一次**近似**，不是用户会看到的画面：

- 断行由 PPTD 自己算，PowerPoint 按自己的度量重新断行；
- 字体度量是估算值，字距、字高与真实渲染有出入；
- 图表由 PPTD 画成形状，PowerPoint 画的是原生图表对象；
- 表格由 PPTD 画成网格，PowerPoint 画的是原生表格。

于是评审模型可能在"通过"一张 PowerPoint 打开就会溢出的页面，也可能在"打回"一张实际没问题的页面。前面几波修的所有排版问题，评审环节都看不见。

本机有 PowerPoint COM，视觉回归基线就是用它渲染的（`tools/visual-regression/export-slides.ps1`），说明这条路在本机是通的。但它有三个现实约束：只在 Windows 上可用、只在装了 Office 的机器上可用、一次要几秒。

## 决策

### 评审优先看真实产物

1. 新增 Tauri 命令 `rasterize_pptx_for_review`：接收导出文稿的原始字节，交给 PowerPoint 逐页渲染成图片，返回每页的图片。
2. 视觉评审循环优先用真实渲染出来的图片。画布渲染降级为备选，只在真实渲染走不通时使用。
3. 评审用的是哪个来源，必须写进质检报告。用户有权知道这份 PPT 是被真实文件挑过毛病，还是只被画布预览挑过。
4. 真实渲染走不通时（没有 PowerPoint、渲染超时、图片解不开），评审**继续进行**，用画布预览代替。降级被明确记为一次降级，并写明原因。
5. 降级不影响文稿产出。已经生成好的 PPT 不会因为渲染不了而消失。

### 二进制不走 JSON

6. 文稿以原始请求体送给后端，不转成 JSON 字节数组。转成数组会让一份几兆的文稿变成几百万个数字，序列化本身就慢到不可接受。这与导出走的是同一条路。
7. 后端把字节写进临时目录，渲染完随临时目录一起销毁。用户文件始终不被覆盖。

### 渲染的边界

8. 宏被显式禁用（`AutomationSecurity = 3`）。机器生成的中间产物不需要也不能执行其中的任何脚本。
9. 逐页导出的文件名由脚本自己定。PowerPoint 自己选的名字是本地化的，中文环境下会得到"幻灯片1.PNG"。
10. 送进评审的文件跳过导出前检查。这个文件只为渲染而存在，而评审要找的问题恰恰是导出前检查会拦下来的那些。
11. 逐页图片转成 JPEG 再送进模型。评审协议本来就只要 JPEG，PNG 直接 base64 传输体积大得多。
12. 缩略图墙由画布渲染和真实渲染共用同一段拼图逻辑，两条路给出的整册缩略图才是可比的。

## 结果

- 视觉评审看的画面与用户打开 PowerPoint 看到的画面来自同一次渲染。
- 评审的来源写在质检报告里，"评审基于真实 PPTX"和"评审基于画布预览"可以被区分。
- 没有 PowerPoint 的机器照常生成，报告里说明降级原因。

实测（本机）：把导出好的 PPTX 交给同一段 PowerShell 脚本，PowerPoint 渲染出 `slide1.png`（1280×720，调色板 PNG，9.4 KB），画面与编辑器里的构图一致。COM 往返约 5–8 秒/份，评审循环最多三轮。

## 未覆盖

- 真实渲染只在本机有 PowerPoint 时可用。macOS 和 Linux 上的评审仍然是画布预览。
- 评审循环每轮都要重新导出并渲染一次，20 页文稿三轮下来多花约 30 秒。没有做内容级缓存：每一轮的设计都在变，缓存命中率本来就低。
- 真实渲染只能反映 PowerPoint 的表现，不能反映 Keynote、WPS 或 Google Slides 的表现。跨渲染器的差异不在本次范围内。
