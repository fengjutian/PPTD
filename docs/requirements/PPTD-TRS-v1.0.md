# PPTD — AI 驱动的 PPT 设计与编辑平台

## 详细技术需求文档（Technical Requirements Specification）

**项目名称：** PPTD  
**文档版本：** V1.0  
**文档状态：** 技术方案已确认，进入开发设计阶段  
**目标平台：** Windows 优先，兼容 macOS  
**应用类型：** 桌面端 AI 演示文稿生成、设计与编辑工具  
**核心技术：** Tauri 2 + Rust + React + TypeScript + Vite

---

# 1. 项目概述

## 1.1 项目目标

PPTD 是一款基于 AI 的桌面端 PPT 生成与设计工具，支持从需求和资料生成演示文稿内容，再通过主题、模板、字体、布局及 3D 图层进行视觉设计，最终导出可在 Microsoft PowerPoint 等常见演示软件中打开的 PPTX 文件。

产品不应仅仅是一个 PPT 图片生成器，而应具备结构化文档模型、页面级编辑、模板解析、主题管理、图层管理和可编辑 PPTX 导出能力。

## 1.2 核心设计原则

### 原则一：内容优先，样式后置

产品工作流必须分成两个阶段：

**阶段一：生成并确认内容。**

- 解析用户需求和输入资料。
- 生成 PPT 大纲及逐页内容。
- 检查逻辑、事实、数据、引用及内容完整性。
- 允许用户编辑、增删页面和确认内容。
- 保存已确认的内容版本。

**阶段二：优化视觉样式。**

- 选择或上传 PPT 模板。
- 识别模板主题、母版和布局。
- 生成视觉设计方案。
- 优化字体、颜色、留白、图表、图片和 3D 效果。
- 检查排版质量并导出 PPTX。

**硬性约束：** 视觉设计 Agent 不得静默修改已确认的标题、正文、数字、事实、引用或页面顺序。若确实需要修改内容，必须生成内容变更记录，并提示用户重新审核受影响页面。

### 原则二：文档模型与渲染引擎分离

所有内容和样式统一存储在 PPTD Document Model 中。

React 编辑器、Three.js 3D 预览、PPTX 导入器及导出器均以该模型为数据基础，不允许各模块分别维护互不一致的文档状态。

### 原则三：优先保证可编辑性

优先将文本、形状、表格、图表和常规图片导出为可编辑的 PPT 原生对象。

复杂 3D 效果允许以图片或视频形式导出，但应尽可能保留标题、说明文字及普通图形的原生编辑能力。

### 原则四：明确兼容性边界

PPTD 必须区分以下能力：

- 新建 PPT 并导出。
- 导入现有 PPTX 并预览。
- 导入现有 PPTX 并修改。
- 高保真保留复杂模板及原有对象。

这四种能力的实现难度不同，不得将“可以打开文件”宣传为“完整支持原文件的高保真编辑”。

# 3. 系统总体架构

## 3.1 架构分层

系统划分为六个主要层次。

### A. UI 层

负责：

- 工作台布局。
- 页面缩略图列表。
- 幻灯片编辑画布。
- 右侧属性面板。
- 模板库、主题库及字体库。
- 图层面板。
- AI 对话和操作记录。
- 导入、导出及兼容性提示。

UI 层不直接修改 PPTX 文件内部结构。

### B. Document Core 层

负责维护统一的 PPT 文档模型，包括：

- 文档元数据。
- 页面及页面顺序。
- 文本、形状、图片、表格和图表。
- 内容版本。
- 设计主题。
- 图层结构。
- 3D 场景引用。
- 导入来源和兼容性信息。
- 撤销重做记录。

Document Core 是整个系统的核心业务层。

### C. Rendering 层

由三个相互独立的引擎组成。

1. **2D Renderer：** React、SVG 和 HTML。
2. **3D Renderer：** Three.js。
3. **Export Renderer：** 将文档模型转换为 PPTX 原生对象或媒体资源。

三个引擎共享文档模型，但不要求使用同一套渲染技术。

### D. AI 层

包含两个权限分离的 Agent：

- Content Agent：负责内容生成、重写、逻辑检查和资料整理。
- Design Agent：负责主题、布局、配色、字体及视觉效果。

两个 Agent 必须使用不同的操作权限和输出 Schema。

### E. File Engine 层

负责：

- PPTX 导入。
- OOXML 解析。
- 模板元数据提取。
- 媒体资源管理。
- PPTX 导出。
- 文件完整性检查。
- 导出兼容性检测。

### F. Persistence 层

负责：

- SQLite 元数据。
- 项目文件。
- 文档版本快照。
- 用户配置。
- 模板元数据。
- 字体元数据。
- 资源文件和缓存。

## 3.2 核心数据流

用户输入资料 → AI 内容生成 → 内容审核 → 内容版本冻结 → 主题与模板选择 → AI 设计生成 → 2D/3D 渲染 → 排版检查 → PPTX 导出 → 导出验证。

内容与样式之间必须存在明确的接口和权限边界。

# 4. 功能需求

## 4.1 项目管理模块

### 功能要求

- 创建、打开、重命名和删除项目。
- 保存项目名称、描述、创建时间和修改时间。
- 支持自动保存及手动保存。
- 支持最近打开项目列表。
- 支持项目复制和另存为。
- 支持文档版本快照。
- 支持异常关闭后的恢复。
- 支持项目资源和缓存管理。

### 数据要求

每个项目至少包含：

- 项目唯一 ID。
- 文档模型。
- 内容版本。
- 设计版本。
- 页面资源。
- 模板引用。
- 字体引用。
- 导入来源信息。
- 导出记录。

### 验收标准

- 重启应用后可以恢复已保存项目。
- 未保存修改必须有明确提示。
- 自动保存失败必须提供可见错误信息。
- 设计修改不能覆盖内容历史版本。

---

## 4.2 AI 内容生成模块

### 输入

- 自然语言需求。
- Markdown、TXT 等文本资料。
- PDF、DOCX 等后续可扩展资料格式。
- 用户上传的现有 PPTX。
- 用户指定的页数、受众、语言和演讲场景。

首期优先支持文本资料与 PPTX 导入。其他格式根据解析成本分阶段实现。

### 输出

Content Agent 必须返回符合 Schema 的结构化数据，至少包括：

- 演示文稿标题。
- 演示目标。
- 大纲。
- 页面列表。
- 每页标题。
- 正文内容。
- 图表需求。
- 图片需求。
- 引用及来源。
- 演讲备注。
- 待确认事项。

AI 输出必须通过 Schema 校验，不能直接以任意 Markdown 字符串作为最终文档数据。

### 内容审核能力

- 修改标题和正文。
- 新增、删除及调整页面顺序。
- 标记事实待核实。
- 标记数字及引用来源。
- 查看 AI 修改建议。
- 对比修改前后的内容。
- 确认或拒绝 AI 提议。
- 保存已确认内容版本。

### 内容状态

每个页面具有以下状态之一：

- Draft：草稿。
- Review：审核中。
- Approved：已确认。
- Changed：确认后发生变更。
- NeedsReview：因依赖内容变化而需要重新审核。

### 验收标准

- 内容生成结果必须通过结构校验。
- AI 不得自动跳过用户要求的内容审核。
- 内容确认后生成可追溯版本。
- 事实核验结果必须区分已验证、待验证和无可靠来源。
- 不得将大模型自身生成的解释当作独立事实来源。

## 4.3 内容与设计隔离机制

这是 PPTD 的核心技术要求。

### Content Model

负责表达演示文稿的语义内容，包括：

- 标题。
- 正文。
- 数字。
- 表格数据。
- 图表语义数据。
- 引用。
- 页面顺序。
- 演讲备注。

### Design Model

负责表达视觉呈现，包括：

- 主题颜色。
- 字体和字号。
- 段落间距。
- 页面布局。
- 元素位置及尺寸。
- 图片裁剪。
- 形状样式。
- 阴影和透明度。
- 3D 场景引用。
- 动画及效果配置。

### 设计 Agent 权限

Design Agent 可以：

- 创建或修改 Design Model。
- 调整元素坐标。
- 提议版式切换。
- 调整字体、颜色和留白。
- 创建图表视觉方案。
- 创建 3D 场景。

Design Agent 不可以直接：

- 修改已确认的标题和正文。
- 修改业务数字。
- 删除已确认页面。
- 改写引用来源。
- 调整页面顺序。

如果布局空间不足，必须返回布局冲突，供用户选择缩小字体、扩展版式、拆分页面或修改内容。

### 内容版本校验

设计任务执行前记录：

- contentRevision。
- documentRevision。
- designRevision。

设计任务执行期间如果内容发生变化，应检测内容版本冲突。

若任务基于旧内容版本生成，必须重新评估受影响页面，不能静默覆盖新版本。

## 4.4 PPT 渲染与编辑画布

### 4.4.1 主编辑画布

采用 React + SVG + HTML。

React 负责组件化与状态管理；SVG 负责矢量对象和几何操作；HTML 负责文本编辑、输入控件及部分交互。

### 支持的对象

- 文本框。
- 标题与段落。
- 矩形、圆形、线条和连接线。
- 图片。
- 常规表格。
- 基础图表。
- 分组对象。
- 占位符。
- 3D 场景预览对象。

### 交互能力

- 选择对象。
- 多选对象。
- 移动、缩放及旋转。
- 对齐和分布。
- 图层前移、后移。
- 复制和粘贴。
- 删除。
- 锁定对象。
- 撤销和重做。
- 网格及参考线。
- 缩放画布。
- 适应窗口。
- 页面级预览。

### 坐标系统

内部文档使用统一的逻辑页面坐标，不依赖当前屏幕像素。

建议内部坐标以 1/1000 英寸或统一逻辑单位表示，导出时转换为 PPTX 所需的 EMU 单位。

画布缩放只影响显示，不应修改实际文档坐标。

### 4.4.2 SVG 与 HTML 使用边界

- SVG：形状、路径、连接线、裁剪和选中框。
- HTML：文本编辑、属性输入、交互控件。
- CSS：界面层视觉和非导出辅助元素。
- Canvas/WebGL：未来用于大量对象的性能优化，不作为首期主编辑层。

编辑器辅助线、选中边框和操作手柄不得导出到 PPTX。

### 4.4.3 性能要求

初期目标：

- 常规页面打开后能够快速完成首次渲染。
- 普通对象移动和缩放应保持流畅。
- 编辑过程中不得因每次鼠标移动而写入完整项目快照。
- 自动保存使用防抖和增量更新。
- 复杂页面应提供性能诊断和对象数量提示。

具体性能指标需在目标 Windows 设备上建立基准测试后确定。

### 4.4.4 专业编辑功能与功能区

编辑器应参考 Microsoft PowerPoint 等成熟演示软件的操作模型，但不得照搬品牌视觉或制造不可用的空按钮。顶部编辑区采用“标签页 + 命令分组”的功能区，至少包含：

- **文件：** 新建、打开/导入、保存、另存为、导出和最近项目。
- **开始：** 撤销/重做、复制/粘贴、页面新建/复制/删除、字体、段落、对象排列。
- **插入：** 文本、图片、基础形状、线条、图标、表格和基础图表。
- **设计：** 页面尺寸、主题、背景、配色和字体方案。
- **排列：** 图层顺序、锁定、组合/取消组合、对齐、等距分布和旋转。
- **视图：** 页面/图层视图、网格、参考线、吸附、缩放和适应窗口。

功能区必须遵守以下约束：

- 只展示当前版本真实可用的命令；后续能力必须明确标注，不得以无响应按钮占位。
- 根据当前页面、选择对象数量和对象类型更新禁用状态及上下文命令。
- 一次功能区操作对应一个领域事务和一个撤销项，不得绕过命令层直接修改文档。
- 常用命令应同时提供工具提示、键盘快捷键和可访问名称。
- 窄窗口允许命令组折叠为菜单，但不得隐藏文件打开、保存、撤销、重做和导出入口。

#### “开始”功能区

“开始”承载高频编辑闭环，至少包括：

- 剪贴板：粘贴、剪切、复制和格式刷；不能访问系统剪贴板时应明确降级为应用内剪贴板。
- 幻灯片：新建、复制、删除、移动、重置版式和页面内容审核状态。
- 字体：字体、字号、增大/减小字号、粗体、斜体、下划线、删除线、文字颜色和清除格式。
- 段落：项目符号、编号、缩进、行距、水平对齐和垂直对齐。
- 绘图：常用形状、填充、轮廓、透明度和快速样式。
- 编辑：查找、替换、全选和选择窗格。

命令只在适用对象上启用；批量格式修改必须形成单个事务，且不得静默修改已审核内容字段。

#### “插入”功能区

“插入”至少包括：

- 新建幻灯片及版式选择。
- 文本框、艺术字和页眉页脚字段。
- 图片、截图和背景图片。
- 矩形、圆形、线条、箭头、连接线和内置图标。
- 原生可编辑表格和基础图表。
- 超链接。

视频、音频、SmartArt、3D 模型和屏幕录制进入后续兼容阶段；在没有文档模型、编辑器和导出器共同支持前，不得显示为可用命令。

### 4.4.5 动画功能

动画是 Design Model 的一部分，不得修改内容文本、数字、引用或页面语义顺序。每个动画使用稳定 ID 并引用稳定 `ElementId`，禁止用数组索引作为持久引用。

基础动画范围：

- 类型：出现、淡化、飞入、浮入、劈裂、擦除、缩放、强调脉冲和消失。
- 阶段：进入、强调和退出。
- 开始方式：单击时、与上一动画同时、上一动画之后。
- 参数：持续时间、延迟、方向和播放顺序。
- 操作：添加、更换、删除、重新排序、复制动画和清除本页动画。
- 预览：当前对象预览、当前页顺序预览和停止预览。

动画领域约束：

- 删除元素时必须同时删除引用该元素的动画。
- 复制元素或页面时必须生成新的动画 ID，并把目标引用改为复制后的元素 ID。
- 锁定元素可以播放动画，但普通编辑命令不得修改其动画。
- 一次“添加/修改/排序动画”对应一个设计事务和一个撤销项，只递增 design/document revision。
- 动画预览属于临时 UI 状态，不改变 revision、保存状态或撤销栈。
- 导入无法解析的动画必须记录原始关系或兼容性警告；不得静默丢失。
- PPTX 导出只有在真实验证为 PowerPoint 可识别时才写入原生动画；否则必须在导出报告中明确记录“动画未导出”，不得用整页视频替代普通页面。

首个增量先交付“动画数据模型、出现/淡化/飞入、三种开始方式、时长/延迟、顺序调整、画布预览和项目持久化”；PPTX 原生动画写入作为独立验收项。

## 4.5 PPT、PPTX 与 PPTD 导入

### 4.5.0 支持格式与处理策略

统一“打开/导入”入口必须接受 `.pptd`、`.pptx` 和 `.ppt`，并根据真实格式选择适配器：

- **PPTD：** 作为原生项目打开，执行 Schema 校验、迁移、资源完整性检查和异常恢复；成功前不得替换当前项目。
- **PPTX：** 作为 OOXML 演示文稿导入，解析可支持对象并建立新的 `PresentationDocument`，同时生成逐项兼容报告。
- **PPT：** 旧版 OLE 二进制格式不得交给 OOXML 解析器。桌面端应通过受控的 Microsoft PowerPoint 或 LibreOffice 转换适配器先转换为临时 `.pptx`，再进入相同的 PPTX 导入流程；本机无可用转换器时必须明确提示，不能假装导入成功。

导入不得覆盖源文件。PPT/PPTX 导入后保存为新的 PPTD 项目；任何对象栅格化、字体替代、动画丢失或不可编辑降级都必须写入导入报告。

### 4.5.1 导入流程

1. 用户从统一入口选择 PPTD、PPTX 或 PPT 文件。
2. 通过文件签名和容器结构识别真实格式，不得只信任扩展名。
3. PPTD 进入项目 Schema 校验与迁移；PPT 在受控临时目录完成兼容转换；PPTX 直接进入 OOXML 流程。
4. 检查文件大小、ZIP/OLE 结构和安全限制。
5. 解析 `[Content_Types].xml`。
6. 读取演示文稿及关系文件。
7. 解析页面尺寸、页面顺序和幻灯片关系。
8. 读取主题、母版和布局。
9. 读取文本、形状、图片及支持的图表。
10. 提取媒体资源。
11. 建立内部文档模型。
12. 生成导入报告及兼容性警告。
13. 渲染预览并允许用户确认后替换当前工作区。

### 4.5.2 需要解析的主要对象

- Presentation。
- Slide。
- Slide Layout。
- Slide Master。
- Theme。
- Shape。
- Text Body。
- Picture。
- Group Shape。
- Table。
- Chart。
- Media Relationship。

### 4.5.3 模板元数据

至少提取：

- 页面尺寸。
- 主题色。
- 主题字体。
- 母版数量。
- 布局数量。
- 页面数量。
- 字体引用。
- 图片和媒体资源。
- 可识别的页面类型。
- 不支持或无法完整解析的对象。

### 4.5.4 模板兼容性分级

- **Level A：** 常规文本、图片、形状和基础表格可解析及编辑。
- **Level B：** 支持基础图表、分组和部分复杂布局。
- **Level C：** 涉及 SmartArt、特殊动画、嵌入对象或高级扩展，需要专门适配或保留原始结构。

兼容等级必须由实际解析结果决定，不得仅根据文件扩展名推断。

### 4.5.5 模板保留模式

提供以下三种模式：

1. **保留原版式：** 尽量沿用原有位置、尺寸及布局。
2. **智能重排：** 允许调整对象位置及版式，但保留已确认内容。
3. **重新设计：** 使用新设计体系重建视觉布局。

对于导入后需要修改的 PPTX，必须明确区分“解析后重建”和“原始 OOXML 定点修改”。

首期不承诺对所有复杂 PPTX 完全无损往返。对不支持对象应明确警告，必要时保留原始资源或限制编辑操作。

- 选择模板应用范围。
- 删除或重命名自定义模板。

### 主题管理

主题由 Design Tokens 表示，至少包含：

- 主色。
- 辅助色。
- 强调色。
- 背景色。
- 正文字色。
- 标题字体。
- 正文字体。
- 标题字号层级。
- 正文字号层级。
- 行距。
- 页面留白。
- 圆角。
- 阴影。
- 图表颜色序列。

### 中国传统色资产与文化主题

PPTD 应支持以中国传统色为基础构建文化类、语文类、历史类和文旅类演示主题。传统色资源的产品形态必须是“颜色原子库 + 语义色板 + 文化场景主题”，不得仅把大量色块平铺成无约束的颜色选择器。

#### 传统色原子库

每个传统色记录至少包含：

- 稳定 ID 和机器可用名称。
- 中文色名、拼音或英文标识。
- HEX 和 RGB 色值。
- 所属基础色系。
- 相对亮度及推荐前景文字颜色。
- 可选的文化语境、出处、版本和来源链接。
- 来源状态：已核验、待核验或用户自定义。
- 使用权或许可说明；来源不明确的资源不得作为内置商业资产发布。

同名传统色在不同资料中出现不同色值时，不得静默合并。系统应保留来源版本，并由主题显式引用确定色值。

#### 研究来源记录

- **名称：** Color Term — 526 Traditional Colors of China。
- **地址：** <https://color-term.com/traditional-color-of-china>
- **访问日期：** 2026-10-23。
- **页面陈述：** 页面称其收录 526 种中国传统色，原始数据来自中国科学院相关名词机构编纂、科学出版社于 1957 年出版的《色谱》（Color Name Dictionary）。该描述属于第三方页面自述，PPTD 不将其自动视为已经完成的权威性或版权核验。
- **当前用途：** 用于主题研究、候选色值比对和来源线索整理；首个“青花瓷韵”主题引用页面可查询的鱼肚白、青灰、靛青、花青、土黄、淡蓝灰和远天蓝色值。
- **发布约束：** 正式发布内置色库前仍需核对原始出版物、数据转载授权、页面内容许可和颜色名称版本差异。若许可不能确认，只保留独立整理后的主题配置和来源说明，不批量复制第三方页面内容、图片或色卡资源。

#### 语义色板

主题不得让 AI 从完整传统色库中随机选色。每个可用主题必须把有限颜色映射到稳定语义角色，至少包括：

- `background`：普通页面背景。
- `surface`：卡片及内容容器背景。
- `primaryText`：标题和主要正文。
- `secondaryText`：辅助文字和注释。
- `primary`：主题主色。
- `accent`：关键结论和高亮色。
- `secondaryAccent`：低频辅助强调色。
- `darkBackground`：封面、章节和结论页的深色节点。
- `onPrimary` 和 `onDark`：对应背景上的可读文字色。
- `chartSeries`：具有足够区分度的图表序列。

主题同时定义各语义色的推荐使用比例、允许组合和禁用组合。主题切换只改变 Design Model，不得修改已审核内容。

#### 首批文化场景主题

首批至少规划以下主题族，正式名称和色值需经过来源及对比度校验后冻结：

- 宋韵雅集：月白、竹青、黛灰和低频赭色，适合古典文学、人文讲座和阅读分享。
- 敦煌壁色：石青、石绿、赭红和藤黄，适合历史、艺术与文博内容。
- 宫墙丹朱：朱砂、暖白、玄青和低频金黄，适合传统建筑、历史和文化专题。
- 江南水墨：米白、青灰、黛蓝和苔绿，适合诗词、地域文化和审美教育。
- 青花瓷韵：瓷白、花青、靛蓝和浅灰，适合清雅的文化课程和作品解读。
- 国潮华章：赤色、暖金、玄色和玉白，适合节庆、品牌及活动展示；不得把高饱和红金用于所有页面。

每套主题至少提供浅色内容页、深色节点页、封面页和图文页预览，不能只展示若干颜色条。

#### 主题详情与选用信息

主题选择界面至少展示：

- 主题名称、文化场景和适用内容类型。
- 语义色板及传统色名称，而不是只有 HEX。
- 浅色页和深色页预览。
- 标题字体、正文字体及字号层级。
- 推荐图片、插图、纹理和装饰风格。
- 推荐使用场景、慎用场景和明确禁忌。
- 色彩对比度与可读性状态。
- 可复制或供 Design Agent 使用的结构化 AI 设计提示词。

#### AI 主题提示词

主题引擎必须能为 Design Agent 生成结构化提示词。提示词至少包含：

- 每个语义色的使用位置和使用比例。
- 封面、章节、普通内容页和结论页的深浅节奏。
- 标题、正文、数字、图表和装饰的配色约束。
- 推荐图片题材、摄影或插画风格及纹理建议。
- 禁止使用的颜色组合、渐变、装饰和字体风格。
- 主题文化气质与当前教学主题的匹配说明。

AI 应使用语义角色和主题约束生成设计，不应直接接收全部传统色列表并自由组合。生成结果仍须通过重复感、主题匹配度、视觉焦点和文字对比度检查。

#### 传统色浏览与自定义

- 完整传统色库属于高级颜色浏览能力，应支持按色系、名称、拼音和色值搜索。
- 默认颜色面板只展示当前主题色、最近使用色和精选传统色，避免一次展示数百个颜色。
- 用户可以把传统色加入自定义色板，但自定义色板必须经过对比度检查后才能保存为可用主题。
- 颜色原子库与主题定义应使用结构化数据维护，并支持将来导出为 CSS Variables、设计令牌或 Figma Variables；首期不承诺与任意第三方 Figma 文件无损同步。

#### 验收标准

- 至少有 6 套可实际应用的文化场景主题，每套包含完整语义角色、字体、页面节奏和 AI 提示词。
- 每套主题至少提供 4 种代表性页面预览，并能应用到测试演示文稿而不修改 Content Model。
- 标题、正文和关键标注在目标背景上的对比度达到产品规定的可读性阈值；不达标时禁止作为默认组合。
- 相同输入和相同主题应得到稳定的基础色板角色，不得由 AI 每次随机改色。
- 主题详情能够说明颜色名称、来源状态、适用场景和禁忌。
- 视觉质量报告包含主题匹配度，并能识别主题色使用失控、强调色过多和连续深色页等问题。
- 未经来源和许可核验的第三方色谱只能作为研究参考，不得直接打包为 PPTD 内置资产。

### 全局主题修改

用户修改主题时，应明确选择：

- 仅修改颜色和字体。
- 修改颜色、字体和基础视觉效果。
- 允许 AI 对页面进行智能重排。

全局主题修改必须支持预览、撤销及应用范围选择。

默认不修改 Content Model。

未经许可证确认，不得自动将字体文件嵌入 PPTX。

## 4.8 3D 图层编辑模块

### 技术实现

采用 Three.js。

React 侧负责编辑器 UI 和状态同步，Three.js 负责 3D 场景、相机、灯光、材质和模型显示。

### 功能范围

- 创建 3D 图层。
- 导入受支持的 3D 模型。
- 创建基础几何体。
- 平移、旋转和缩放。
- 设置材质及灯光。
- 控制相机视角。
- 设置透视参数。
- 预览场景。
- 将场景绑定到指定幻灯片。
- 保存场景参数。
- 将 3D 场景转换为可导出的媒体资源。

### 坐标系统

必须区分：

1. 3D 世界坐标。
2. 相机观察坐标。
3. 最终幻灯片上的投影区域。

旋转相机用于查看场景时，不得意外改变最终幻灯片中的投影构图。

只有用户执行“应用视角”或“更新投影”等明确操作时，才更新用于导出的视角参数。

### 3D 导出策略

首期使用混合导出方式：

- 普通文字：PPT 原生文本。
- 普通形状：PPT 原生形状。
- 常规图表：PPT 原生图表，条件允许时优先。
- 复杂 3D 场景：高分辨率图片。
- 需要动态展示的场景：后续评估视频导出。
- 原生 3D 模型嵌入：后续版本研究 OOXML 支持与目标 Office 版本兼容性。

不应将完整 3D 场景全部转换成单张图片，否则将损失文字、形状及图表的可编辑性。

## 4.9 PPTX 导出模块

### 首期导出范围

- 幻灯片尺寸。
- 页面顺序。
- 文本框。
- 字体、字号、颜色及基础段落样式。
- 基础形状。
- 图片。
- 表格。
- 基础图表。
- 页面背景。
- 3D 场景图片。
- 演讲备注的可行性评估与后续支持。

### 导出流程

1. 校验文档模型。
2. 检查内容版本和审核状态。
3. 检查字体。
4. 检查对象溢出、遮挡及坐标异常。
5. 生成导出计划。
6. 将原生对象转换为 PPTX 元素。
7. 导出媒体资源。
8. 生成 PPTX 包。
9. 检查 ZIP 和 OOXML 结构。
10. 在可用环境中执行 PPTX 转 PDF 验证。
11. 输出文件和导出报告。

### 导出模式

- **标准导出：** 面向新建 PPT，优先使用 PptxGenJS。
- **模板保留导出：** 面向导入后修改的 PPTX，通过 OOXML 适配层处理。
- **预览导出：** 输出 PDF 或图片用于检查。

不能假设 PptxGenJS 可以完整保留任意原始 PPTX 的所有对象和扩展属性。

### 验收标准

- PPTX 文件结构有效。
- 常见 Office 软件可以打开测试文件。
- 常规文字、图片和形状仍可编辑。
- 导出前后页面数量与顺序一致。
- 不存在未告知用户的内容变化。
- 不支持的对象在导出报告中有明确记录。

# 5. 核心数据模型

## 5.1 Document Model

建议的逻辑结构：

```ts
interface PresentationDocument {
  id: string;
  title: string;
  schemaVersion: number;

  contentRevision: number;
  designRevision: number;
  documentRevision: number;

  pageSize: {
    width: number;
    height: number;
    unit: "emu";
  };

  content: ContentModel;
  design: DesignModel;
  slides: SlideModel[];

  source?: ImportSource;
  compatibility?: CompatibilityReport;
}
```

## 5.2 Content Model

```ts
interface ContentModel {
  outline: OutlineNode[];
  references: ReferenceItem[];
  metadata: {
    audience?: string;
    language?: string;
    objective?: string;
  };
}

interface SlideContent {
  title: string;
  blocks: ContentBlock[];
  speakerNotes?: string;
  status: "draft" | "review" | "approved" | "changed" | "needs_review";
  contentHash?: string;
}

type ContentBlock = TextBlock | TableDataBlock | ChartDataBlock | ImageBriefBlock;
```

上述为逻辑接口示例。正式实现时应补充 ID、来源追踪、Schema 校验和版本迁移规则。

## 5.3 Design Model

```ts
interface DesignModel {
  themeId?: string;
  tokens: DesignTokens;
  layouts: LayoutDefinition[];
  assets: DesignAsset[];
}

interface SlideModel {
  id: string;
  contentId: string;
  layoutId?: string;
  elements: SlideElement[];
}

interface SlideElement {
  id: string;
  type: "text" | "shape" | "image" | "table" | "chart" | "group" | "scene3d";

  x: number;
  y: number;
  width: number;
  height: number;
  rotation?: number;

  style?: Record<string, unknown>;
  sourceContentId?: string;
  locked?: boolean;
}
```

生产代码必须进一步将不同对象类型拆分成独立、强类型的接口，避免使用过多无约束的 `Record<string, unknown>`。

## 5.4 3D 场景模型

3D 场景与幻灯片元素分开保存。

至少包括：

- Scene ID。
- 模型资源引用。
- 世界坐标。
- 材质参数。
- 灯光参数。
- 相机参数。
- 导出投影参数。
- 目标幻灯片 ID。
- 渲染分辨率。
- 资源版本。

3D 场景更新不应直接覆盖幻灯片中的其他对象。

## 5.5 版本机制

至少维护三种版本：

- 内容版本。
- 设计版本。
- 文档整体版本。

当用户修改内容时，递增内容版本；当用户修改主题或布局时，递增设计版本；所有持久化修改均更新整体版本。

版本历史应支持查看差异和恢复。

# 6. AI 服务接口

## 6.1 Provider Adapter

统一大模型接口，避免将某个模型服务商写死在业务层。

建议定义：

```ts
interface AIProvider {
  generateStructured<T>(request: StructuredGenerationRequest): Promise<StructuredGenerationResult<T>>;

  streamText(request: TextGenerationRequest, onChunk: (chunk: string) => void): Promise<void>;
}
```

具体实现应处理：

- API 配置。
- 模型选择。
- 超时。
- 取消请求。
- 错误重试。
- 限流。
- Schema 校验。
- Token 和成本统计。
- 日志脱敏。

API Key 不得写入前端源码、项目文件或日志。

## 6.2 Content Agent

输入：用户需求、资料、目标受众、页数约束。

输出：符合 Content Model Schema 的内容提案。

权限：只能提出内容变更；涉及已确认内容时，必须通过用户确认流程。

## 6.3 Design Agent

输入：已确认内容版本、主题、模板元数据、页面尺寸和设计约束。

输出：符合 Design Model Schema 的设计提案。

权限：只能修改设计相关字段，不得直接提交内容字段修改。

## 6.4 Agent 执行安全

- AI 输出必须经过结构校验。
- AI 不得直接执行任意系统命令。
- 文件操作必须经过授权的本地服务接口。
- 网络请求范围应明确。
- 外部导入内容视为不可信数据。
- 任何可能覆盖原文件的操作都必须经过确认。
- 长任务支持取消、状态显示及错误恢复。

# 9. 安全与稳定性要求

## 9.1 文件安全

- 对上传文件进行大小限制。
- 校验 ZIP 包和 XML 结构。
- 防止路径穿越。
- 限制解压后的总资源大小。
- 处理损坏、循环关系和异常 XML。
- 不执行文件内的宏或外部脚本。
- 保留原始文件，默认不覆盖用户输入的 PPTX。

## 9.2 Tauri 安全

- 使用最小权限原则配置 Tauri capabilities。
- 前端不能任意访问文件系统。
- 文件读写通过受控命令执行。
- 对外部 URL 和网络请求进行约束。
- 不将秘密信息暴露给 WebView。
- 发布版本关闭不必要的调试能力。

## 9.3 稳定性

- 自动保存。
- 崩溃恢复。
- 任务取消。
- 长任务进度显示。
- 文件写入采用临时文件与安全替换策略。
- 导出失败保留可诊断日志。
- 重要操作提供撤销或恢复方案。

- 应用崩溃后恢复。

## 10.3 兼容性测试

- 图表。
- 分组对象。
- 多母版。

- 在不分叉 `PresentationDocument`、领域命令和内容/设计隔离规则的前提下提供浏览器端。

**交付标准：** 用户无需安装客户端即可通过受控链接查看、评论和编辑云项目；多人协作无静默丢失或越权写入；桌面与 Web 对同一领域命令产生等价文档结果。

# 12. 全局验收标准

PPTD 首个可用版本必须满足以下条件：

1. 用户可以新建和保存演示文稿。
2. 用户可以编辑标题、正文、图片及常见形状。
3. 用户可以导出可打开的 PPTX。
4. 用户可以通过统一入口打开 PPTD，并导入代表性 PPTX/PPT 文件查看解析结果和兼容报告。
5. 用户可以选择模板并修改全局主题。
6. 用户可以管理字体并查看缺失字体提示。
7. AI 内容生成和 AI 样式优化必须分阶段执行。
8. 内容审核完成后可以保存独立版本。
9. 样式修改不得静默修改已确认内容。
10. 内容发生变化时可以追踪差异并重新审核。
11. 3D 场景能够独立编辑和保存。
12. 普通 PPT 对象和复杂 3D 对象采用适当的混合导出策略。
13. 导出失败时能够提供错误信息，不损坏原始项目。
14. 对不支持的 PPTX 对象必须有明确提示。
15. 项目具备基本自动化测试、兼容性测试和许可证记录。

# 13. 开发执行约束

为了保证后续 AI 辅助编程不偏离产品目标，开发过程中应遵守以下约束：

- 先建立数据模型和渲染边界，再开发复杂 UI。
- 不得将 PPT 全部转换成图片作为常规导出方案。
- 不得把 PptxGenJS 当作完整的 PPTX 导入和保真编辑引擎。
- 不得让 Design Agent 直接覆盖 Content Model。
- 不得在未验证许可证的情况下打包或嵌入字体。
- 不得以单一测试文件证明全部 PPTX 兼容性。
- 不得在尚未完成基础 2D 编辑器时优先投入完整 3D 编辑功能。
- 每个阶段必须具备可运行版本、自动化测试和明确的验收条件。
- 复杂模板的支持范围必须以实际测试结果为准。

**最终产品定位：PPTD 是以结构化文档模型为核心、以 AI 内容生成和视觉设计为两阶段工作流、以 React/SVG 作为 2D 编辑层、以 Three.js 作为 3D 编辑层、以 OOXML 和 PPTX 导出引擎实现文件交付的桌面优先、后续支持浏览器与云协作的演示文稿平台。**
