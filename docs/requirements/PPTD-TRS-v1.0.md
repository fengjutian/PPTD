# PPTD — AI 驱动的 PPT 设计与编辑平台
## 详细技术需求文档（Technical Requirements Specification）

**项目名称：** PPTD  
**文档版本：** V1.0  
**文档状态：** 技术方案已确认，进入开发设计阶段  
**目标平台：** Windows 优先，兼容 macOS  
**应用类型：** 桌面端 AI 演示文稿生成、设计与编辑工具  
**核心技术：** Tauri 2 + Rust + React + TypeScript + Vite

---

# 1. 项目概述

## 1.1 项目目标

PPTD 是一款基于 AI 的桌面端 PPT 生成与设计工具，支持从需求和资料生成演示文稿内容，再通过主题、模板、字体、布局及 3D 图层进行视觉设计，最终导出可在 Microsoft PowerPoint 等常见演示软件中打开的 PPTX 文件。

产品不应仅仅是一个 PPT 图片生成器，而应具备结构化文档模型、页面级编辑、模板解析、主题管理、图层管理和可编辑 PPTX 导出能力。

## 1.2 核心设计原则

### 原则一：内容优先，样式后置

产品工作流必须分成两个阶段：

**阶段一：生成并确认内容。**

- 解析用户需求和输入资料。
- 生成 PPT 大纲及逐页内容。
- 检查逻辑、事实、数据、引用及内容完整性。
- 允许用户编辑、增删页面和确认内容。
- 保存已确认的内容版本。

**阶段二：优化视觉样式。**

- 选择或上传 PPT 模板。
- 识别模板主题、母版和布局。
- 生成视觉设计方案。
- 优化字体、颜色、留白、图表、图片和 3D 效果。
- 检查排版质量并导出 PPTX。

**硬性约束：** 视觉设计 Agent 不得静默修改已确认的标题、正文、数字、事实、引用或页面顺序。若确实需要修改内容，必须生成内容变更记录，并提示用户重新审核受影响页面。

### 原则二：文档模型与渲染引擎分离

所有内容和样式统一存储在 PPTD Document Model 中。

React 编辑器、Three.js 3D 预览、PPTX 导入器及导出器均以该模型为数据基础，不允许各模块分别维护互不一致的文档状态。

### 原则三：优先保证可编辑性

优先将文本、形状、表格、图表和常规图片导出为可编辑的 PPT 原生对象。

复杂 3D 效果允许以图片或视频形式导出，但应尽可能保留标题、说明文字及普通图形的原生编辑能力。

### 原则四：明确兼容性边界

PPTD 必须区分以下能力：

- 新建 PPT 并导出。
- 导入现有 PPTX 并预览。
- 导入现有 PPTX 并修改。
- 高保真保留复杂模板及原有对象。

这四种能力的实现难度不同，不得将“可以打开文件”宣传为“完整支持原文件的高保真编辑”。

# 3. 系统总体架构

## 3.1 架构分层

系统划分为六个主要层次。

### A. UI 层

负责：

- 工作台布局。
- 页面缩略图列表。
- 幻灯片编辑画布。
- 右侧属性面板。
- 模板库、主题库及字体库。
- 图层面板。
- AI 对话和操作记录。
- 导入、导出及兼容性提示。

UI 层不直接修改 PPTX 文件内部结构。

### B. Document Core 层

负责维护统一的 PPT 文档模型，包括：

- 文档元数据。
- 页面及页面顺序。
- 文本、形状、图片、表格和图表。
- 内容版本。
- 设计主题。
- 图层结构。
- 3D 场景引用。
- 导入来源和兼容性信息。
- 撤销重做记录。

Document Core 是整个系统的核心业务层。

### C. Rendering 层

由三个相互独立的引擎组成。

1. **2D Renderer：** React、SVG 和 HTML。
2. **3D Renderer：** Three.js。
3. **Export Renderer：** 将文档模型转换为 PPTX 原生对象或媒体资源。

三个引擎共享文档模型，但不要求使用同一套渲染技术。

### D. AI 层

包含两个权限分离的 Agent：

- Content Agent：负责内容生成、重写、逻辑检查和资料整理。
- Design Agent：负责主题、布局、配色、字体及视觉效果。

两个 Agent 必须使用不同的操作权限和输出 Schema。

### E. File Engine 层

负责：

- PPTX 导入。
- OOXML 解析。
- 模板元数据提取。
- 媒体资源管理。
- PPTX 导出。
- 文件完整性检查。
- 导出兼容性检测。

### F. Persistence 层

负责：

- SQLite 元数据。
- 项目文件。
- 文档版本快照。
- 用户配置。
- 模板元数据。
- 字体元数据。
- 资源文件和缓存。

## 3.2 核心数据流

用户输入资料 → AI 内容生成 → 内容审核 → 内容版本冻结 → 主题与模板选择 → AI 设计生成 → 2D/3D 渲染 → 排版检查 → PPTX 导出 → 导出验证。

内容与样式之间必须存在明确的接口和权限边界。

# 4. 功能需求

## 4.1 项目管理模块

### 功能要求

- 创建、打开、重命名和删除项目。
- 保存项目名称、描述、创建时间和修改时间。
- 支持自动保存及手动保存。
- 支持最近打开项目列表。
- 支持项目复制和另存为。
- 支持文档版本快照。
- 支持异常关闭后的恢复。
- 支持项目资源和缓存管理。

### 数据要求

每个项目至少包含：

- 项目唯一 ID。
- 文档模型。
- 内容版本。
- 设计版本。
- 页面资源。
- 模板引用。
- 字体引用。
- 导入来源信息。
- 导出记录。

### 验收标准

- 重启应用后可以恢复已保存项目。
- 未保存修改必须有明确提示。
- 自动保存失败必须提供可见错误信息。
- 设计修改不能覆盖内容历史版本。

---

## 4.2 AI 内容生成模块

### 输入

- 自然语言需求。
- Markdown、TXT 等文本资料。
- PDF、DOCX 等后续可扩展资料格式。
- 用户上传的现有 PPTX。
- 用户指定的页数、受众、语言和演讲场景。

首期优先支持文本资料与 PPTX 导入。其他格式根据解析成本分阶段实现。

### 输出

Content Agent 必须返回符合 Schema 的结构化数据，至少包括：

- 演示文稿标题。
- 演示目标。
- 大纲。
- 页面列表。
- 每页标题。
- 正文内容。
- 图表需求。
- 图片需求。
- 引用及来源。
- 演讲备注。
- 待确认事项。

AI 输出必须通过 Schema 校验，不能直接以任意 Markdown 字符串作为最终文档数据。

### 内容审核能力

- 修改标题和正文。
- 新增、删除及调整页面顺序。
- 标记事实待核实。
- 标记数字及引用来源。
- 查看 AI 修改建议。
- 对比修改前后的内容。
- 确认或拒绝 AI 提议。
- 保存已确认内容版本。

### 内容状态

每个页面具有以下状态之一：

- Draft：草稿。
- Review：审核中。
- Approved：已确认。
- Changed：确认后发生变更。
- NeedsReview：因依赖内容变化而需要重新审核。

### 验收标准

- 内容生成结果必须通过结构校验。
- AI 不得自动跳过用户要求的内容审核。
- 内容确认后生成可追溯版本。
- 事实核验结果必须区分已验证、待验证和无可靠来源。
- 不得将大模型自身生成的解释当作独立事实来源。

## 4.3 内容与设计隔离机制

这是 PPTD 的核心技术要求。

### Content Model

负责表达演示文稿的语义内容，包括：

- 标题。
- 正文。
- 数字。
- 表格数据。
- 图表语义数据。
- 引用。
- 页面顺序。
- 演讲备注。

### Design Model

负责表达视觉呈现，包括：

- 主题颜色。
- 字体和字号。
- 段落间距。
- 页面布局。
- 元素位置及尺寸。
- 图片裁剪。
- 形状样式。
- 阴影和透明度。
- 3D 场景引用。
- 动画及效果配置。

### 设计 Agent 权限

Design Agent 可以：

- 创建或修改 Design Model。
- 调整元素坐标。
- 提议版式切换。
- 调整字体、颜色和留白。
- 创建图表视觉方案。
- 创建 3D 场景。

Design Agent 不可以直接：

- 修改已确认的标题和正文。
- 修改业务数字。
- 删除已确认页面。
- 改写引用来源。
- 调整页面顺序。

如果布局空间不足，必须返回布局冲突，供用户选择缩小字体、扩展版式、拆分页面或修改内容。

### 内容版本校验

设计任务执行前记录：

- contentRevision。
- documentRevision。
- designRevision。

设计任务执行期间如果内容发生变化，应检测内容版本冲突。

若任务基于旧内容版本生成，必须重新评估受影响页面，不能静默覆盖新版本。

## 4.4 PPT 渲染与编辑画布

### 4.4.1 主编辑画布

采用 React + SVG + HTML。

React 负责组件化与状态管理；SVG 负责矢量对象和几何操作；HTML 负责文本编辑、输入控件及部分交互。

### 支持的对象

- 文本框。
- 标题与段落。
- 矩形、圆形、线条和连接线。
- 图片。
- 常规表格。
- 基础图表。
- 分组对象。
- 占位符。
- 3D 场景预览对象。

### 交互能力

- 选择对象。
- 多选对象。
- 移动、缩放及旋转。
- 对齐和分布。
- 图层前移、后移。
- 复制和粘贴。
- 删除。
- 锁定对象。
- 撤销和重做。
- 网格及参考线。
- 缩放画布。
- 适应窗口。
- 页面级预览。

### 坐标系统

内部文档使用统一的逻辑页面坐标，不依赖当前屏幕像素。

建议内部坐标以 1/1000 英寸或统一逻辑单位表示，导出时转换为 PPTX 所需的 EMU 单位。

画布缩放只影响显示，不应修改实际文档坐标。

### 4.4.2 SVG 与 HTML 使用边界

- SVG：形状、路径、连接线、裁剪和选中框。
- HTML：文本编辑、属性输入、交互控件。
- CSS：界面层视觉和非导出辅助元素。
- Canvas/WebGL：未来用于大量对象的性能优化，不作为首期主编辑层。

编辑器辅助线、选中边框和操作手柄不得导出到 PPTX。

### 4.4.3 性能要求

初期目标：

- 常规页面打开后能够快速完成首次渲染。
- 普通对象移动和缩放应保持流畅。
- 编辑过程中不得因每次鼠标移动而写入完整项目快照。
- 自动保存使用防抖和增量更新。
- 复杂页面应提供性能诊断和对象数量提示。

具体性能指标需在目标 Windows 设备上建立基准测试后确定。

## 4.5 PPTX 导入与模板解析

### 4.5.1 导入流程

1. 用户选择 PPTX 文件。
2. 检查扩展名、文件大小和 ZIP 包结构。
3. 解析 `[Content_Types].xml`。
4. 读取演示文稿及关系文件。
5. 解析页面尺寸、页面顺序和幻灯片关系。
6. 读取主题、母版和布局。
7. 读取文本、形状、图片及支持的图表。
8. 提取媒体资源。
9. 建立内部文档模型。
10. 生成导入报告及兼容性警告。
11. 渲染预览并允许用户确认。

### 4.5.2 需要解析的主要对象

- Presentation。
- Slide。
- Slide Layout。
- Slide Master。
- Theme。
- Shape。
- Text Body。
- Picture。
- Group Shape。
- Table。
- Chart。
- Media Relationship。

### 4.5.3 模板元数据

至少提取：

- 页面尺寸。
- 主题色。
- 主题字体。
- 母版数量。
- 布局数量。
- 页面数量。
- 字体引用。
- 图片和媒体资源。
- 可识别的页面类型。
- 不支持或无法完整解析的对象。

### 4.5.4 模板兼容性分级

- **Level A：** 常规文本、图片、形状和基础表格可解析及编辑。
- **Level B：** 支持基础图表、分组和部分复杂布局。
- **Level C：** 涉及 SmartArt、特殊动画、嵌入对象或高级扩展，需要专门适配或保留原始结构。

兼容等级必须由实际解析结果决定，不得仅根据文件扩展名推断。

### 4.5.5 模板保留模式

提供以下三种模式：

1. **保留原版式：** 尽量沿用原有位置、尺寸及布局。
2. **智能重排：** 允许调整对象位置及版式，但保留已确认内容。
3. **重新设计：** 使用新设计体系重建视觉布局。

对于导入后需要修改的 PPTX，必须明确区分“解析后重建”和“原始 OOXML 定点修改”。

首期不承诺对所有复杂 PPTX 完全无损往返。对不支持对象应明确警告，必要时保留原始资源或限制编辑操作。

- 强调色。
- 背景色。
- 正文字色。
- 标题字体。
- 正文字体。
- 标题字号层级。
- 正文字号层级。
- 行距。
- 页面留白。
- 圆角。

## 4.7 字体库

### 功能

- 搜索字体。
- 字体预览。
- 中英文混排预览。
- 收藏字体。
- 设置标题及正文字体。
- 检测缺失字体。
- 提供替代字体建议。
- 查看字体来源和许可证。
- 管理用户安装的字体。
- 记录导出时使用的字体信息。

### 字体选择原则

优先评估：

- Inter。
- Noto Sans SC。
- Source Han Sans。
- Source Han Serif。

实际使用时必须逐款确认许可证及对应字体文件的再分发、嵌入和商业使用权限。

### 导出约束

应用内部可显示某种字体，并不意味着接收者的电脑一定安装了该字体。

导出前应检查：

- 字体是否存在。
- 字体是否允许嵌入。
- 是否需要替代字体。
- 替代后可能产生的换行和尺寸变化。

未经许可证确认，不得自动将字体文件嵌入 PPTX。

## 4.8 3D 图层编辑模块

### 技术实现

采用 Three.js。

React 侧负责编辑器 UI 和状态同步，Three.js 负责 3D 场景、相机、灯光、材质和模型显示。

### 功能范围

- 创建 3D 图层。
- 导入受支持的 3D 模型。
- 创建基础几何体。
- 平移、旋转和缩放。
- 设置材质及灯光。
- 控制相机视角。
- 设置透视参数。
- 预览场景。
- 将场景绑定到指定幻灯片。
- 保存场景参数。
- 将 3D 场景转换为可导出的媒体资源。

### 坐标系统

必须区分：

1. 3D 世界坐标。
2. 相机观察坐标。
3. 最终幻灯片上的投影区域。

旋转相机用于查看场景时，不得意外改变最终幻灯片中的投影构图。

只有用户执行“应用视角”或“更新投影”等明确操作时，才更新用于导出的视角参数。

### 3D 导出策略

首期使用混合导出方式：

- 普通文字：PPT 原生文本。
- 普通形状：PPT 原生形状。
- 常规图表：PPT 原生图表，条件允许时优先。
- 复杂 3D 场景：高分辨率图片。
- 需要动态展示的场景：后续评估视频导出。
- 原生 3D 模型嵌入：后续版本研究 OOXML 支持与目标 Office 版本兼容性。

不应将完整 3D 场景全部转换成单张图片，否则将损失文字、形状及图表的可编辑性。

---

## 4.9 PPTX 导出模块

### 首期导出范围

- 幻灯片尺寸。
- 页面顺序。
- 文本框。
- 字体、字号、颜色及基础段落样式。
- 基础形状。
- 图片。
- 表格。
- 基础图表。
- 页面背景。
- 3D 场景图片。
- 演讲备注的可行性评估与后续支持。

### 导出流程

1. 校验文档模型。
2. 检查内容版本和审核状态。
3. 检查字体。
4. 检查对象溢出、遮挡及坐标异常。
5. 生成导出计划。
6. 将原生对象转换为 PPTX 元素。
7. 导出媒体资源。
8. 生成 PPTX 包。
9. 检查 ZIP 和 OOXML 结构。
10. 在可用环境中执行 PPTX 转 PDF 验证。
11. 输出文件和导出报告。

### 导出模式

- **标准导出：** 面向新建 PPT，优先使用 PptxGenJS。
- **模板保留导出：** 面向导入后修改的 PPTX，通过 OOXML 适配层处理。
- **预览导出：** 输出 PDF 或图片用于检查。

不能假设 PptxGenJS 可以完整保留任意原始 PPTX 的所有对象和扩展属性。

### 验收标准

- PPTX 文件结构有效。
- 常见 Office 软件可以打开测试文件。
- 常规文字、图片和形状仍可编辑。
- 导出前后页面数量与顺序一致。
- 不存在未告知用户的内容变化。
- 不支持的对象在导出报告中有明确记录。


## 5.4 3D 场景模型

3D 场景与幻灯片元素分开保存。

至少包括：

- Scene ID。
- 模型资源引用。
- 世界坐标。
- 材质参数。
- 灯光参数。
- 相机参数。
- 导出投影参数。
- 目标幻灯片 ID。
- 渲染分辨率。
- 资源版本。

3D 场景更新不应直接覆盖幻灯片中的其他对象。

## 5.5 版本机制

至少维护三种版本：

- 内容版本。
- 设计版本。
- 文档整体版本。

当用户修改内容时，递增内容版本；当用户修改主题或布局时，递增设计版本；所有持久化修改均更新整体版本。

版本历史应支持查看差异和恢复。

# 6. AI 服务接口

## 6.1 Provider Adapter

统一大模型接口，避免将某个模型服务商写死在业务层。

建议定义：

```ts
interface AIProvider {
  generateStructured<T>(
    request: StructuredGenerationRequest
  ): Promise<StructuredGenerationResult<T>>;

  streamText(
    request: TextGenerationRequest,
    onChunk: (chunk: string) => void
  ): Promise<void>;
}
```

具体实现应处理：

- API 配置。
- 模型选择。
- 超时。
- 取消请求。
- 错误重试。
- 限流。
- Schema 校验。
- Token 和成本统计。
- 日志脱敏。

API Key 不得写入前端源码、项目文件或日志。

## 6.2 Content Agent

输入：用户需求、资料、目标受众、页数约束。

输出：符合 Content Model Schema 的内容提案。

权限：只能提出内容变更；涉及已确认内容时，必须通过用户确认流程。

## 6.3 Design Agent

输入：已确认内容版本、主题、模板元数据、页面尺寸和设计约束。

输出：符合 Design Model Schema 的设计提案。

权限：只能修改设计相关字段，不得直接提交内容字段修改。

## 6.4 Agent 执行安全

- AI 输出必须经过结构校验。
- AI 不得直接执行任意系统命令。
- 文件操作必须经过授权的本地服务接口。
- 网络请求范围应明确。
- 外部导入内容视为不可信数据。
- 任何可能覆盖原文件的操作都必须经过确认。
- 长任务支持取消、状态显示及错误恢复。

# 9. 安全与稳定性要求

## 9.1 文件安全

- 对上传文件进行大小限制。
- 校验 ZIP 包和 XML 结构。
- 防止路径穿越。
- 限制解压后的总资源大小。
- 处理损坏、循环关系和异常 XML。
- 不执行文件内的宏或外部脚本。
- 保留原始文件，默认不覆盖用户输入的 PPTX。

## 9.2 Tauri 安全

- 使用最小权限原则配置 Tauri capabilities。
- 前端不能任意访问文件系统。
- 文件读写通过受控命令执行。
- 对外部 URL 和网络请求进行约束。
- 不将秘密信息暴露给 WebView。
- 发布版本关闭不必要的调试能力。

## 9.3 稳定性

- 自动保存。
- 崩溃恢复。
- 任务取消。
- 长任务进度显示。
- 文件写入采用临时文件与安全替换策略。
- 导出失败保留可诊断日志。
- 重要操作提供撤销或恢复方案。

# 12. 全局验收标准

PPTD 首个可用版本必须满足以下条件：

1. 用户可以新建和保存演示文稿。
2. 用户可以编辑标题、正文、图片及常见形状。
3. 用户可以导出可打开的 PPTX。
4. 用户可以导入代表性 PPTX 文件并查看解析结果。
5. 用户可以选择模板并修改全局主题。
6. 用户可以管理字体并查看缺失字体提示。
7. AI 内容生成和 AI 样式优化必须分阶段执行。
8. 内容审核完成后可以保存独立版本。
9. 样式修改不得静默修改已确认内容。
10. 内容发生变化时可以追踪差异并重新审核。
11. 3D 场景能够独立编辑和保存。
12. 普通 PPT 对象和复杂 3D 对象采用适当的混合导出策略。
13. 导出失败时能够提供错误信息，不损坏原始项目。
14. 对不支持的 PPTX 对象必须有明确提示。
15. 项目具备基本自动化测试、兼容性测试和许可证记录。

# 13. 开发执行约束

为了保证后续 AI 辅助编程不偏离产品目标，开发过程中应遵守以下约束：

- 先建立数据模型和渲染边界，再开发复杂 UI。
- 不得将 PPT 全部转换成图片作为常规导出方案。
- 不得把 PptxGenJS 当作完整的 PPTX 导入和保真编辑引擎。
- 不得让 Design Agent 直接覆盖 Content Model。
- 不得在未验证许可证的情况下打包或嵌入字体。
- 不得以单一测试文件证明全部 PPTX 兼容性。
- 不得在尚未完成基础 2D 编辑器时优先投入完整 3D 编辑功能。
- 每个阶段必须具备可运行版本、自动化测试和明确的验收条件。
- 复杂模板的支持范围必须以实际测试结果为准。

**最终产品定位：PPTD 是以结构化文档模型为核心、以 AI 内容生成和视觉设计为两阶段工作流、以 React/SVG 作为 2D 编辑层、以 Three.js 作为 3D 编辑层、以 OOXML 和 PPTX 导出引擎实现文件交付的桌面应用。**
