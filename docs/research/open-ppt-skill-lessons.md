# open-ppt-skill 对 PPTD 的可借鉴点分析

> 调研对象：[jinwyp/open-ppt-skill](https://github.com/jinwyp/open-ppt-skill)  
> 调研日期：2026-10-23  
> 结论性质：外部项目调研，不构成 PPTD 的需求基线或架构决策；正式采纳长期方案时仍需更新 TRS 或新增 ADR。

## 1. 结论摘要

`open-ppt-skill` 最值得 PPTD 借鉴的是一条完整、可操作的交付闭环：

```text
Agent 生成结构化中间文档
  → 本地可视化编辑
  → 导出可编辑 PPTX
  → 渲染整册与逐页图片
  → 多模态视觉检查
  → 定点修复问题页
  → 再次导出与复检
```

这条思路与 PPTD 的产品方向高度一致，但两者定位不同：`open-ppt-skill` 是面向 Coding Agent 的 Skill、CLI 和本地浏览器编辑器，PPTD 是具备强领域模型、事务、版本、审核和安全边界的桌面编辑平台。因此应借鉴它的工作流、主题令牌、分文件交付、视觉复检和 Agent 使用约束，不应直接照搬其 PPTD YAML、像素坐标模型、逆向协议或 patched WASM。

PPTD 当前已经实现了其中相当一部分思想，包括结构化 Document Model、可编辑 PPTX、主题预设、真实 PPTX 渲染后的视觉评审、自动保存、导出报告和内容/设计隔离。后续的主要增量不是重建另一套格式，而是把现有能力进一步产品化、夹具化并形成可复用的 Agent 工作流。

## 2. 对比定位

| 维度      | open-ppt-skill                           | PPTD                                            | 判断                                       |
| --------- | ---------------------------------------- | ----------------------------------------------- | ------------------------------------------ |
| 产品形态  | Agent Skill + CLI + 本地浏览器编辑器     | Tauri 桌面应用 + React 编辑器                   | 可借鉴工作流，不照搬外壳                   |
| 中间模型  | YAML 清单 + 每页 `.page` 文件            | 强类型、带 Schema 版本的 `PresentationDocument` | PPTD 模型更适合作为内部事实来源            |
| 几何单位  | 像素，约定 `1px = 1pt`                   | 整数 EMU                                        | 保持 PPTD 的 EMU，不采用像素持久化         |
| 页面组织  | 每页自包含、清单引用页面和媒体           | 单一聚合根、稳定 ID、资源引用                   | 可研究分片存储，但不能破坏事务与引用不变量 |
| PPTX 导出 | 本地前端镜像 + patched WASM              | PptxGenJS + OOXML 后处理/验证                   | 不引入不透明的逆向导出链                   |
| 人工编辑  | 浏览器文件夹授权、自动保存               | 桌面端受控文件命令、自动保存和恢复              | PPTD 的安全与恢复边界更完整                |
| 视觉质检  | 导出图片、拼接总览、多模态检查、修复复检 | 已有真实 PPTX 栅格化、逐页/整册视觉评审和质量门 | 高度一致，可继续吸收夹具与报告呈现方式     |
| 内容治理  | 生成指令主要约束 Agent 行为              | 内容/设计模型、revision、审核状态和权限隔离     | PPTD 不应退化为仅靠提示词约束              |
| 可编辑性  | 文本、形状、图片等保持可编辑             | 原生对象优先，降级进入结构化报告                | 方向一致                                   |

## 3. 建议借鉴的内容

### 3.1 把 Agent 工作流固化为“可执行规范”

该项目的 `SKILL.md` 不只是提示词，而是包含前置环境检查、输入分类、设计路径选择、生成步骤、导出要求和质检动作的操作规程。PPTD 可以为自身的 Content Agent 和 Design Agent 分别建立版本化工作流规范：

- 明确任务输入是主题、完整文档、逐页大纲、模板还是风格参考。
- 在执行前检查模型能力、视觉评审开关、渲染器和导出器是否可用。
- 将生成、设计、质检、修复、交付拆成可报告进度的阶段。
- 每个阶段明确输入 Schema、输出 Schema、取消行为、失败降级和用户可见说明。
- 把“最终必须交付项目源文件和 PPTX”作为产品策略，而不是依赖 Agent 临场决定。

PPTD 已经有 Provider Adapter、流式进度、取消和视觉评审端口，适合把这些能力上升为可测试的工作流定义，而不是新增另一套 Agent 专用文档模型。

### 3.2 双交付物与自包含项目包

`open-ppt-skill` 默认同时交付可继续编辑的项目目录和 PPTX 成品，并要求页面、媒体等依赖位于项目目录内部。这个做法值得保留为 PPTD 的明确交付原则：

- `.pptd` 项目是可追溯、可迁移、可再次编辑的事实来源。
- `.pptx` 是面向 PowerPoint/WPS/LibreOffice 的交换与演示成品。
- 所有本地资源进入受控项目资源目录，以内容哈希或稳定资源 ID 引用。
- 导出记录关联源文档 revision、导出时间、导出器版本和结构化报告。

与外部项目不同，PPTD 不应将“项目源文件 + PPTX”理解为两个并列真源；PPTX 是不可变快照的派生物，不能反向覆盖当前项目状态。

### 3.3 逐页分片的可诊断性与增量处理

外部项目采用“清单 + 每页独立文件 + media”结构，使 Agent 能只修改某一页，也使人工审查和版本 diff 更直观。PPTD 当前以 `PresentationDocument` 聚合根保证跨页事务和不变量，不能简单改成松散页面文件，但可以借鉴其优点：

- 保存层可研究内部快照分片、页级内容哈希或增量日志，聚合根仍是逻辑真源。
- 视觉评审、缩略图、缓存和导出计划按页面指纹复用未变化结果。
- 诊断报告以稳定 `slideId` 关联问题页，不依赖数组下标或文件名。
- 提供“导出可读诊断包”能力，包含脱敏后的清单、页级摘要、资源索引和报告，方便复现问题。

该方向若改变持久化格式，必须单独立项，提供迁移、固定样例和保存中断测试。

### 3.4 主题令牌、样式继承和可见的优先级

外部 PPTD 规范把颜色、字体、文本样式等抽为主题令牌，并定义清楚的样式优先级。PPTD 已在 ADR 0031 中借鉴 `theme.textStyles + $token` 的思想，后续可以继续补强：

- 统一颜色角色、字阶、段落节奏、图表系列色和组件样式令牌。
- 为“主题默认 → 页面/布局 → 元素 → 文本片段”的覆盖关系建立单一解析器。
- 在属性面板显示属性来自主题、布局还是元素覆盖，并支持“恢复为主题值”。
- 导出报告记录主题字体和颜色是否真实写入 PPTX，而不是只判断画面相似。
- 主题预设附带适用场景、密度、可读性约束和预览夹具，而不只是配色缩略图。

### 3.5 真实导出结果驱动的视觉复检

该项目强调在交付前导出整册页面图和总览图，检查变形、遮挡、越界、对比度、排版和文字溢出，再只修复问题页。PPTD 已经采用“优先评审真实 PPTX 渲染，画布渲染只作降级”的更严格方案，建议继续吸收以下产品化细节：

- 同时保留逐页大图和整册 contact sheet：前者看细节，后者看节奏与一致性。
- 视觉问题必须包含 `slideId`、问题类型、证据、建议和检查来源。
- 未变化页面复用上轮结论；问题页修复后定点重渲染、重评审。
- 报告区分“确定性检查通过”“视觉模型通过”“未检查/部分覆盖”，不合并成一个模糊的成功状态。
- 将代表性主题、中文字体、图表、表格、裁剪、旋转、深浅页面节奏纳入固定视觉夹具。

这些方向与现有 ADR 0017、0022、0037 一致，不需要引入新的渲染技术，只需继续完善交互、覆盖率和回归样例。

### 3.6 预设主题库与示例驱动验收

外部项目用多套命名明确的 design system 降低“只给主题、不说风格”导致的输出波动，并提供完整示例项目供编辑器和导出链验证。PPTD 已有主题预设，应进一步做到：

- 每个预设至少有封面、章节、正文、指标、表格、图表、图片和结论页样例。
- 预设包含设计意图、受众、密度、字体回退、深浅页节奏和禁用组合。
- AI 只能从结构化预设和设计意图生成设计命令，不能复制未经审核的坐标脚本。
- 示例项目既是产品展示，也是 Schema 迁移、导出兼容和视觉回归夹具。

### 3.7 本地优先和最小文件权限

外部项目仅监听 `127.0.0.1`，浏览器获得用户授权后才访问目录，保存端拒绝绝对路径和 `..` 越界。这与 PPTD 的安全原则一致。PPTD 应保持更严格的桌面边界：

- WebView 不取得任意文件系统访问权，所有操作继续通过窄 Tauri command。
- 打开、保存、导出和资源导入都在 Rust 端再次规范化并验证范围、扩展名和大小。
- 远程图片和字体必须经过下载策略、大小限制、类型嗅探和缓存隔离。
- 视觉评审上传页面图必须受用户设置控制，并在报告中显示是否发生外发。

## 4. 不建议直接采用的内容

### 4.1 不采用其 YAML PPTD 作为 PPTD 内部领域模型

外部格式以 Agent 易写和每页自包含为首要目标，使用像素坐标、数组顺序表达层级，并宣称可与 PPTX 双向转换。PPTD 的核心要求则是稳定 ID、整数 EMU、内容/设计分离、revision、事务、撤销重做、迁移和明确的兼容边界。直接兼容该格式会引入第二套事实来源，并弱化现有不变量。

若未来确有互操作需求，应把它定义为外部导入/导出适配器，并生成兼容报告；不要把它命名为 PPTD 原生格式，也不要承诺无损往返。

### 4.2 不采用 patched WASM 或逆向前端作为核心导出器

该仓库明确说明其实现基于对 Kimi Slides、PPTD 格式和公开前端协议的逆向分析，兼容协议可能随上游更新失效。其编辑器还包含本地镜像和 patched WASM。即使仓库采用 MIT 许可证，也不能据此推定被镜像或修改的第三方前端资源、字体、协议和二进制都具备同等授权。

PPTD 应继续使用可审计的 PptxGenJS 和自有 OOXML 适配层，并以真实测试报告兼容范围。任何第三方实现只能作为黑盒行为参考或测试样本；在完成来源、许可证、商标、字体和二进制供应链审计前，不得复制代码或打包资产。

### 4.3 不采用“像素即点”的几何约定

`1px = 1pt` 对 Agent 编写 YAML 很直观，但会混淆显示像素、排版点和 OOXML EMU，也容易在缩放、不同 DPI、PowerPoint 往返时产生误差。PPTD 应保持内部 EMU，UI 层只做显示换算，字体仍以 pt 值对象表达。

### 4.4 不依赖提示词保障内容安全与版本一致性

外部 Skill 主要靠步骤和文字要求约束 Agent。PPTD 的内容与设计隔离是领域不变量，必须由不同 Schema、命令权限、revision 校验、内容指纹和审核状态执行。外部工作流规范可以增强行为，但不能替代代码级权限。

### 4.5 不把字体嵌入和动画写入当作默认承诺

字体嵌入涉及字体许可、嵌入权限位、文件体积和不同办公软件的兼容性；动画写入也必须在真实 PowerPoint 中验证。PPTD 应继续遵循“验证后才宣称支持”的原则，并在导出报告中分别记录已嵌入、被替代、未嵌入、已导出、未验证和被降级状态。

## 5. 与 PPTD 当前实现的关系

| 外部项目做法       | PPTD 当前状态                                         | 后续动作                                   |
| ------------------ | ----------------------------------------------------- | ------------------------------------------ |
| 结构化中间层       | 已有强类型 Document Model、Schema 和迁移              | 保持现有模型，不新增 YAML 真源             |
| 可编辑 PPTX        | 已有原生文本、图片、形状、表格、图表导出              | 继续扩充兼容夹具与报告                     |
| 主题令牌/预设      | 已有主题字阶令牌和多套预设，ADR 0031 已明确参考该项目 | 增加来源可见性、恢复主题值和预设验收页     |
| 自动保存与人工微调 | 桌面编辑器已具备保存/恢复和编辑闭环                   | 强化导出 revision 关联和诊断包             |
| 逐页视觉检查       | 已有视觉评审和确定性质量门                            | 增加 contact sheet、问题证据和定点复检体验 |
| 真实 PPTX 渲染检查 | ADR 0022 已要求优先检查真实导出结果                   | 扩充 PowerPoint/LibreOffice 差异样本       |
| 失败降级           | 已有“不以未检查冒充通过”的执行边界                    | 在所有报告和 UI 状态保持统一措辞           |
| Agent Skill 工作流 | 已有服务与端口，但缺少面向任务的统一操作规程          | 建立 Content/Design 两套版本化工作流规范   |
| 每页独立文件       | 当前采用聚合根和项目 JSON                             | 仅研究内部增量持久化，不改变领域边界       |

## 6. 建议落地顺序

### P0：文档和质量闭环，不改变 Schema

1. 为 AI 生成建立版本化执行清单：前置检查、输入分类、阶段进度、取消和降级。
2. 为视觉评审增加整册 contact sheet，并在报告中区分逐页与整册结论。
3. 扩充主题预设示例项目，让同一批夹具同时服务展示、视觉回归和导出兼容测试。
4. 在导出记录中明确关联 `documentRevision`、`contentRevision`、`designRevision` 和导出器版本。

### P1：增强可诊断性和增量处理

1. 用页级内容/设计指纹缓存缩略图、栅格图和视觉评审结果。
2. 让问题页支持定点修复、定点重渲染和复检，未变化页复用结论。
3. 增加可脱敏的诊断包，便于复现项目、字体、资源和导出差异。
4. 在属性面板显示样式值来源，并支持恢复主题值。

### P2：需要单独 ADR 或需求变更的探索

1. 研究项目持久化的页级分片或增量日志，但保持 `PresentationDocument` 聚合边界。
2. 若有生态互操作需求，设计外部 YAML PPTD 的沙箱化导入适配器与兼容报告。
3. 评估字体嵌入的许可、格式和目标软件兼容矩阵。
4. 对动画导出建立真实 PowerPoint 验证夹具后，再扩大能力声明。

## 7. 建议验收场景

- 修改一页后重新质检，只重渲染和重评审该页；整册节奏评审仍重新执行。
- 视觉模型不可用时仍生成 PPTX，报告明确显示“未执行视觉评审”，不显示“通过”。
- 每套主题预设都能生成固定示例，画布、真实 PPTX 渲染和导出报告可交叉核对。
- 导出报告可追溯到确切 revision；导出期间继续编辑不会改变正在导出的快照。
- 字体未安装、禁止嵌入或嵌入失败时，报告给出不同的稳定错误/警告码。
- 外部项目包包含越界路径、绝对路径或超大远程资源时被拒绝，且当前项目不被替换。
- 内容已审核后执行设计修复，内容指纹保持不变；若内容不足以容纳，返回冲突而不是删改文字。

## 8. 风险与法律注意事项

- 仓库代码标注为 MIT，不等于其中镜像的第三方前端、字体、WASM 和协议实现均可直接再分发。
- 项目自述为非官方逆向实现，并提示上游变化可能使兼容协议失效；不适合成为 PPTD 的生产运行时依赖。
- “PPTX 转 PPTD 后继续修改”不应被理解为完整 OOXML 无损往返。PPTD 仍需按对象类型和真实测试结果给出兼容等级。
- 外部项目的示例、主题名称和视觉资产若要用于产品内置资源，必须逐项核验版权、商标和字体许可证。
